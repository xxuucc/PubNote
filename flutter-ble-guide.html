01

全景架构：一屏记住七层

你的代码永远只碰到最上面四层，但故障永远从下面三层冒上来。

三个「先别写代码」的检查点

  • 硬件确认 BLE：项目立项时确认硬件用 BLE，这一条写在《需求-硬件对齐表》第一行。经典蓝牙 BR/EDR 没有跨平台方案。
  • 协议先于界面：帧格式、命令字、CRC 算法、序号规则没定，UI 写得再顺也只能返工。
  • 权限先于流程：先说明页、再请求权限，被永久拒绝要有去设置页的路径——这条同时是 iOS 审核要求。
02

原理底座：不懂这些，固件第一次提协议你会听不懂

BLE 的所有「玄学问题」都能在 ATT 层找到物理解释：为什么必须以 20 字节设计分包、为什么命令队列必须串行、为什么订阅也会撞 GATT 错误。

2.1 先分清三样东西

技术典型设备Flutter 支持度
经典蓝牙 BR/EDR耳机、音箱、键盘、打印机、HC-05基本无跨平台方案（flutter_bluetooth_serial 仅 Android）；选 BLE 芯片可绕开
BLE 低功耗手环、传感器、锁、POS、灯✅ 主战场，生态成熟
BLE Mesh智能灯组网手机端可用但要走 Provisioner 角色，生态小众，先不碰

2.2 GAP 角色模型

  • Central（中心）：扫描广播、发起连接 → 手机 App 几乎总是这个角色。
  • Peripheral（外设）：发广播、被连接 → App 当「被连接方」是进阶需求（如给电脑配对）。
  • 广播者 / 观察者：纯 beacon 场景。

⚠️ Central ≠ Server

GATT Client/Server 是数据层概念，与 GAP 角色（Central / Peripheral / Advertiser / Observer）可以交叉：手机（Central）连上外设后，手机是 GATT Client，外设是 GATT Server。这句搞混，和固件的对话会从一开始就错位。

2.3 GATT 数据模型与 ATT 协议（业务 90% 在这里）

Profile → Service(服务) → Characteristic(特征) → Descriptor(描述符)
概念你要记住的
UUID官方服务用 16 位短码（如 0x180F 电量）；私有业务用 128 位 UUID，和固件一起定
Read / WriteWrite 分 withResponse（可靠、慢） 和 withoutResponse（快、可能丢）
Notify vs IndicateNotify 无 ACK（高频），Indicate 有 ACK（可靠）；订阅本质是写 CCCD 描述符 0x2902
MTUATT 默认 23 → 有效载荷仅 20 字节；协商后可到 247~517。协议永远按 20B 设计分包，把大 MTU 当优化
Properties每个特征声明支持哪些操作，读固件文档对齐
★ 原理深入：ATT 层——「串味 bug」的真正根因（关联 05 命令队列、第 08 章帧格式）

GATT 是建立在 ATT（Attribute Protocol） 之上的应用框架，一切 GATT 操作最终都是 ATT 的 PDU（Read Request / Write Request / Handle Value Notification 等）。理解这一层，很多玄学问题就有了物理解释：

  1. 为什么 write withResponse 慢：一条 Write Request 是一个完整的 ATT 事务（PDU 往返），在当前 connection interval 内必须等对端回应答才能开始下一个事务——这就是命令队列必须串行的底层原因。
  2. 为什么 withoutResponse 快：Write Command 是单向 PDU，塞进当前连接事件的剩余空隙即可，无需往返——但正因为无确认，连续快发会塞满外设的接收缓冲导致丢包（坑 #8）。
  3. 为什么 MTU 减 3 = 有效载荷：ATT PDU 头占 3 字节（Opcode 1B + Handle 2B），故 MTU=23 时有效 20B；MTU=247 时有效 244B（write without response 无需 handle 字段，可多用 2 字节）。
  4. 为什么订阅也占写通道：订阅 Notify 的本质是向 CCCD（0x2902）发一条 ATT Write Request——所以订阅操作也必须走命令队列，不能与其他写并发。

2.4 广播与扫描

  • 经典广播 = 31B 主广播 + 31B ScanResponse；BLE 5 扩展广播单包最大 255B，链式包可拼到约 1650B——需要更大载荷时按链式设计，但注意扩展广播的外设芯片支持度参差。
  • 关键字段：本地名（极易被截断）、服务 UUID 列表、厂商数据 Company ID（2B）+ payload、Service Data。
  • iBeacon 的本质是 Apple 厂商数据格式；iOS 上检测 iBeacon 必须用 CoreLocation，CoreBluetooth 扫不到（FBP 明确不支持）。iOS 18+ 走 AccessorySetupKit 时系统直接返回 accessory 对象，同样绕过 CB 的 iBeacon 解析路径。
  • 扫描即耗电、即后台受限，永远用硬件级 ScanFilter（withServices / 厂商数据前缀）而不是到了 Dart 层再过滤——Dart 层过滤救不了电量和 Android 的扫描启动限频。

2.5 连接参数与吞吐（和固件一起谈的「性能三件套」）

  • Connection Interval（7.5ms~4s）：决定 notify 延迟和吞吐；Android 可调 requestConnectionPriority；iOS 由系统私下谈，App 无法指定。
  • 7.5ms 下限是 Bluetooth Core ≤ 6.1 的规范；Core 6.2（2025-11）已把最小连接间隔降至 375μs。当前多数外设芯片尚未跟进 6.2，按 7.5ms 与固件对线依然成立，但协议文档应写明依据版本，避免芯片厂商质疑。
  • Supervision Timeout：多久没报文算断开 → 这是「假连接」之源，和固件协商一致（协议统一为 1000ms）。
  • 吞吐量级参考：7.5ms interval + DLE + 247 MTU + withoutResponse，理论峰值 ~100KB/s 级，实测通常 60~90KB/s；别期待流媒体级吞吐。
★ 原理深入：Supervision Timeout 与连接参数的耦合——「假连接」的真正机制（关联坑 #5、M2 心跳看门狗）

链路层约定：Peripheral 在 Supervision Timeout 内未收到任何来自 Central 的包 → 判定链路丢失。但实践中「App 显示已连接、设备不响应」的机制是：

  1. App 调 requestConnectionPriority → Android 栈发出 Connection Parameter Update Request；
  2. 若外设固件未正确响应（拒绝 / 无响应 / 回了非法参数），部分手机栈会让链路停留在违反规范的参数区间；
  3. 链路层实际已无法收发，但双方都未触发 Supervision Timeout（timeout 的判定依赖「收到包重置计时器」，参数无效时双方状态机各自卡死）；
  4. 结果：App 侧状态「已连接」，实际链路已死。

排查命令：

adb
adb shell dumpsys bluetooth_manager

看 LE Connection 段的 interval / latency / timeout 数值，验证是否满足 Core 规范约束：interval × (latency + 1) × 2 < supervision timeout。不满足即为此症。

工程对策：M2 阶段实现「心跳 + 假连接看门狗」（3 次心跳超时主动 disconnect + 重连），不依赖系统判定。

2.6 配对 / 绑定与安全

  • 配对 = 建立密钥；绑定 = 存密钥长期复用。
  • Just Works（无交互确认）/ Passkey（输码）/ OOB；LE Secure Connections。
  • 系统级加密 ≠ 业务安全：鉴权令牌、防重放序号要在你的应用层协议里自己设计（协议中的 SEQ 序号机制即承担防重放的第一层职责）。
03

平台差异：第一坑埋区

同一份 Dart 代码，Android 要三段权限、iOS 要一句文案、Web 只能被用户手势唤起。差异不在 API，在权限与后台模型。

3.1 Android 权限时间线（必背）

API 级别要求
≤ 28BLUETOOTH / BLUETOOTH_ADMIN 静态 + ACCESS_COARSE_LOCATION
29–30ACCESS_FINE_LOCATION 且系统定位服务必须开着，否则扫描零结果
31+（Android 12）动态请求 BLUETOOTH_SCAN（neverForLocation 标记可绕开定位）+ BLUETOOTH_CONNECT；不再需要定位权限
13–14MTU 行为变化（首个 GATT 客户端主导 517）；前台服务需绑定 foregroundServiceType="connectedDevice"
15 / 16后台扫描 / 连接需前台服务配合，系统杀后台更激进

neverForLocation 的决策要点

加此标记后 Android 12+ 扫描不再需要定位权限；但若业务同时要基于蓝牙广播做位置推断（如室内定位），就必须保留定位权限、不加此标记——这是 Android 强制的反「扫描定位推断」保护。二选一：不能既要扫描、又不要定位权限、又用广播数据推断位置。

3.2 iOS / macOS（审核 + 后台重灾区）

  • NSBluetoothAlwaysUsageDescription 必填，文案含糊会被拒审——写清「连接什么设备、做什么用」。
  • 后台模式：UIBackgroundModes: bluetooth-central（做客户端）/ bluetooth-peripheral（当外设）；配合 State Restoration 才能在被杀后被系统重新唤醒（约 10 秒处理窗口）。
  • 拿不到 MAC 地址：iOS identifier 是随机 UUID 且重装会变 → 设备唯一识别靠应用层（序列号 / 配网绑定时上报云端），不要把 remoteId 当持久身份。
  • iOS 的 MTU 由系统谈，不能主动 request。
  • iOS 18+ 出现 AccessorySetupKit：系统级附件配对 UI，大一统体验但限制多（universal_ble 已封装 picker）；ASK 直接返回 accessory 对象，绕过 CB 的 iBeacon 解析路径。
  • macOS：App Sandbox 需开 Bluetooth 硬件权限（见 *.entitlements）。

3.3 桌面与 Web

平台底层限制
WindowsWinRT权限 / 配对模型不同，选型需支持 WinRT 的插件
LinuxBlueZ / D-BusMTU 不可控
WebWeb Bluetooth仅 Chrome / Edge；requestDevice 必须由用户手势触发；无后台

3.4 后台与常驻

  • iOS：bluetooth-central + stateRestore，处理逻辑要在 10s 内完事。
  • Android：前台服务（connectedDevice 类型）+ flutter_foreground_task / workmanager 做周期性重连巡检。
  • 国产 ROM 杀后台是常态：引导用户加白名单，但不要承诺「永不被杀」。

05

代码架构：插件必须被关在 feature 里

用成熟插件意味着通道已经被替你设计好了，代码架构的重点只剩「别让插件类型漏进业务层」。

5.1 用成熟插件：重点是「用好」

  • 插件回调来自平台线程（不是系统主线程 UI），用 Riverpod / State 即可，不需要额外 handler。
  • 高频 notify（如 50Hz IMU）别每个包 setState，在 service 层合并节流。
  • 监听生命周期：统一 cancelWhenDisconnected / unsubscribe，防止重复订阅（FBP 社区问题榜第一名）。
  • FBP / universal_ble 都支持 mock，可做单元测试。

5.2 自研通道（特殊需求才走）：Pigeon 优于手写 MethodChannel

  • Pigeon 类型安全 codegen，数据面用 Uint8List 走 BinaryCodec。
  • 经典拆分：命令面 + 事件面（notify / 扫描 / 断线）。
  • 自研时必须定义统一错误分类（连接 / 权限 / 超时 / 设备主动断 / 未知）和超时重试策略，否则两端原生实现各写各的。

三条关键设计原则（各有原理支撑）

  1. 插件类型不外泄（包在本 feature 内）→ 将来换插件 / 自研通道不动业务。
  2. 一切写操作经命令队列，绝不允许并发写同一个特征——每次 Write withResponse 都是一个完整 ATT 事务，并发必然冲突。
  3. 协议文档（第 08 章）是双端「源码」，固件每次变更版本号递增、App 校验兼容性。
06

落地：M0–M4 里程碑与 M1 骨架

五个里程碑可直接排期。M0 没做，后面所有返工都由它引起；M1 的验收标准是「能连上并能收命令应答」，不是「界面好看」。

  1. 需求与硬件协议对齐

    0.5–2 天 · 影响后面所有 · 交付物见第 08 章

    和固件工程师共签《协议书》：布局图、命令表（帧头 / 长度 / 命令字 / 参数 / CRC 算法）、MTU 预期、广播字段（Company ID、产品码）、配对 / bonding、OTA 方案、协议版本号机制。

    ⚠️ 没有这一步的 BLE 项目后期返工率最高。

  2. 工程骨架 + 扫描连接 Demo

    0.5–1 周 · 完整代码见本章 6.2–6.12

    • flutter create，装 universal_ble（或选定的插件），两端权限全配。
    • 权限先行 UX：先说明页再请求权限，被永久拒绝引导去设置。
    • 扫描列表页（名称、RSSI、厂商信息）+ 连接 / 断开，用 nRF Connect 做交叉验证。

  3. 协议打通 + 核心链路

    1–2 周 · 心跳与假连接看门狗在这里落地

    • discoverServices → 订阅 notify → 帧解析（CRC / 序号校验）→ 命令队列接入。
    • 心跳 + 假连接看门狗（3 次超时主动 disconnect + 重连）——机制依据见 2.5。
    • 断线重连：指数退避（1s / 2s / 4s…上限 30s）+ UI 状态同步。

  4. 生产化

    2–4 周 · OTA 与后台是主要工作量

    • OTA（分包 + CRC + ACK + 断点 + 进度 UI，协议见 8.5）、配对 / bonding 流程。
    • 后台：Android FGS + iOS restoreState。
    • 日志分级 + 现场问题可回传（设备名 / 命令摘要 / RSSI）。

  /// Android ≤11：FINE_LOCATION；iOS：蓝牙权限系统统一弹窗
  static Future<PermResult> ensureScanPermissions() async {
    if (Platform.isIOS || Platform.isMacOS) {
      final s = await Permission.bluetooth.status;
      if (s.isGranted) return PermResult.granted;
      final r = await Permission.bluetooth.request();
      return r.isGranted ? PermResult.granted
          : (r.isPermanentlyDenied ? PermResult.permanentlyDenied : PermResult.denied);
    }
    if (Platform.isAndroid) {
      if (await _sdkInt() >= 31) {
        final scan = await Permission.bluetoothScan.request();
        final conn = await Permission.bluetoothConnect.request();
        if (scan.isGranted && conn.isGranted) return PermResult.granted;

          return PermResult.permanentlyDenied;

      if (loc.isGranted) return PermResult.granted;

6.8 frame_codec.dart · 帧编解码 + CRC16
lib/features/device/ble/frame_codec.dart
import 'dart:typed_data';
/// 应用层帧：[0xA5][len][seq][cmd][payload...][crc16_lo][crc16_hi]
/// CRC16-CCITT (poly 0x1021, init 0xFFFF)，字节序 Little-Endian
class FrameCodec {
  static const frameHead = 0xA5;
  static const headerLen = 4;   // head + len + seq + cmd
  static const crcLen    = 2;
  static Uint8List encode(int seq, int cmd, Uint8List payload) {
    final len = 1 + 1 + payload.length; // seq + cmd + payload
    final out = Uint8List(headerLen + payload.length + crcLen);
    out[0] = frameHead;
    out[1] = len;
    out[2] = seq & 0xFF;
    out[3] = cmd;
    out.setRange(4, 4 + payload.length, payload);
    final crc = crc16Ccitt(out.sublist(0, 4 + payload.length));
    out[out.length - 2] = crc & 0xFF;
    out[out.length - 1] = (crc >> 8) & 0xFF;
    return out;
  }
  /// 校验 + 解码；返回 null 表示非法帧
  static (int seq, int cmd, Uint8List payload)? decode(Uint8List raw) {
    if (raw.length < headerLen + crcLen) return null;
    if (raw[0] != frameHead) return null;
    final len = raw[1];
    final total = 2 + len + crcLen;              // head+len + len字节 + crc
    if (raw.length < total) return null;
    final body = raw.sublist(0, 2 + len);        // CRC 覆盖域
    final crcExpect = raw[2 + len] | (raw[2 + len + 1] << 8);
    final crcActual = crc16Ccitt(body);
    if (crcExpect != crcActual) return null;
    // payload 区间为 [4, 2+len)
    final payload = Uint8List.sublistView(raw, headerLen, 2 + len);
    return (raw[2], raw[3], payload);
  }
  static int crc16Ccitt(List<int> data) {
    var crc = 0xFFFF;
    for (final b in data) {
      crc ^= b << 8;
      for (var i = 0; i < 8; i++) {
        crc = (crc & 0x8000) != 0 ? ((crc << 1) ^ 0x1021) & 0xFFFF : (crc << 1) & 0xFFFF;
      }
    }
    return crc;
  }
}
6.9 command_queue.dart · 单设备串行命令队列（架构原则 #2）
lib/features/device/ble/command_queue.dart
import 'dart:async';
import 'dart:typed_data';
import 'frame_codec.dart';
/// 单设备串行命令队列
/// 设计依据：Write withResponse = 完整 ATT 事务（见 2.3），必须串行
class CommandQueue {
  CommandQueue({required Future<void> Function(Uint8List) writeFn,
                required Stream<Uint8List> notifyStream})
      : _writeFn = writeFn, _notifySub = notifyStream.listen(_onNotify);
  final Future<void> Function(Uint8List) _writeFn;
  final StreamSubscription<Uint8List> _notifySub;
  final _tasks = <_Task>[];
  bool _busy = false;
  int _seq = 0;
  bool _closed = false;
  Uint8List? _lastNotify;
  void _onNotify(Uint8List v) => _lastNotify = v;
  Future<Uint8List> send(int cmd, Uint8List payload,
      {Duration timeout = const Duration(seconds: 3),
       bool expectNotify = true,
       int maxRetries = 1}) {
    if (_closed) return Future.error(StateError('queue closed'));
    final c = Completer<Uint8List>();
    _tasks.add(_Task(seq: ++_seq & 0xFF, cmd: cmd, payload: payload,
                     timeout: timeout, expectNotify: expectNotify,
                     maxRetries: maxRetries, completer: c));
    _pump();
    return c.future;
  }
  Future<void> _pump() async {
    if (_busy || _tasks.isEmpty) return;
    _busy = true;
    final t = _tasks.removeAt(0);
    var attempt = 0;
    while (attempt <= t.maxRetries) {
      _lastNotify = null;
      final frame = FrameCodec.encode(t.seq, t.cmd, t.payload);
      try {
        await _writeFn(frame);
        final result = await _waitForResponse(t);
        t.completer.complete(result);
        break;
      } catch (_) {
        attempt++;
        if (attempt > t.maxRetries) {
          t.completer.completeError(TimeoutException('cmd 0x${t.cmd.toRadixString(16)} timeout'));
        } else {
          await Future.delayed(const Duration(milliseconds: 200));
        }
      }
    }
    _busy = false;
    _pump();
  }
  Future<Uint8List> _waitForResponse(_Task t) async {
    final ackCmd = t.cmd | 0x80;                 // 应答帧约定：cmd|0x80
    final sw = Stopwatch()..start();
    while (sw.elapsed < t.timeout) {
      final n = _lastNotify;
      if (n != null) {
        final decoded = FrameCodec.decode(n);
        // 应答匹配：序号一致 且 cmd == 请求|0x80（或协议错误帧 0xFF）
        if (decoded != null && decoded.$1 == t.seq &&
            (decoded.$2 == ackCmd || decoded.$2 == 0xFF)) {
          return decoded.$3;
        }
      }
      if (!t.expectNotify) {
        await Future.delayed(const Duration(milliseconds: 50));
        return Uint8List(0);
      }
      await Future.delayed(const Duration(milliseconds: 10));
    }
    throw TimeoutException('no response for seq=${t.seq}');
  }
  void close() {
    _closed = true;
    for (final t in _tasks) {
      t.completer.completeError(StateError('queue closed'));
    }
    _tasks.clear();
    _notifySub.cancel();
  }
}
class _Task {
  _Task({required this.seq, required this.cmd, required this.payload,
         required this.timeout, required this.expectNotify,
         required this.maxRetries, required this.completer});
  final int seq, cmd, maxRetries;
  final Uint8List payload;
  final Duration timeout;
  final bool expectNotify;
  final Completer<Uint8List> completer;
}

★ 坑 #5 专述：GATT_ERROR 133 的机理与处置优先级

133 对应 HAL 层 GATT_ERROR（0x85），底层常见触发：连接参数协商失败、连接已占用未释放、controller 内部状态机异常、广播 PDU 校验失败、配对超时。

处置顺序（按收益排序）：

  1. gatt.close() 释放后 250~500ms 退避重试（最多 3 次）；
  2. refresh() 反射清 GATT 缓存（API 未公开但广泛使用）；
  3. 切换 TRANSPORT_LE（connectGatt(context, autoConnect, callback, TRANSPORT_LE)）；
  4. 检查外设广播 interval 是否过密（<100ms 的广播会显著增加 133 概率）。

Android 14+ 上 133 出现率显著上升；新版插件（FBP / universal_ble）内部已加自动重试，自研通道必须自己实现这套处置。

8.1 传输层约定

项约定
MTU 策略协议按 MTU=23（有效载荷 20B）设计分包；MTU 协商成功后可单帧承载更多 payload，但固件必须兼容 20B 场景

连接参数Connection Interval 协商目标 15~30ms（依据 Core 6.1 的 7.5ms~4s 区间，见 2.5）；Supervision Timeout 双端统一 1000ms
写特征Write With Response（控制命令）；高频数据可单独开 withoutResponse 通道（另行协商）
Notify高优先级数据走 Notify；应答帧也走 Notify
串行约束同一时刻只能有一个未完成的 ATT 写事务（App 命令队列串行）；固件不应主动并发 notify 多条业务消息到同一 CCCD

8.2 帧格式（App ↔ 固件 双向统一）

frame layout
偏移  长度  字段       说明
0     1    HEADER     0xA5（固定帧头）
1     1    LEN        seq+cmd+payload 总长度（1 + 1 + N），不含帧头/CRC
2     1    SEQ        序号 0x00~0xFF 循环递增；App 请求与固件应答共用一个序号
3     1    CMD        命令字（请求）；应答 = CMD | 0x80（见 8.3）
4..N  N    PAYLOAD    变长负载，N = LEN - 2
N+4   2    CRC16      CRC16-CCITT(0x1021, init 0xFFFF)，覆盖 HEADER..PAYLOAD 全部字节，
                      低字节在前

总帧长：4 + N + 2 字节。MTU=23 时最大 payload N=17；MTU=247 时最大 N=241。

8.4 CRC16-CCITT 参考实现（双端对拍用）

dart · crc16Ccitt
int crc16Ccitt(List<int> data) {
  var crc = 0xFFFF;
  for (final b in data) {
    crc ^= b << 8;
    for (var i = 0; i < 8; i++) {
      crc = (crc & 0x8000) != 0 ? ((crc << 1) ^ 0x1021) & 0xFFFF : (crc << 1) & 0xFFFF;
    }
  }
  return crc;
}
c · crc16_ccitt
uint16_t crc16_ccitt(const uint8_t *data, size_t len) {
    uint16_t crc = 0xFFFF;
    for (size_t i = 0; i < len; i++) {
        crc ^= (uint16_t)data[i] << 8;
        for (int b = 0; b < 8; b++) {
            crc = (crc & 0x8000) ? ((crc << 1) ^ 0x1021) & 0xFFFF
                                 : (crc << 1) & 0xFFFF;
        }
    }
    return crc;
}

8.5 OTA 分包协议

OTA flow
[App] ─ OTA_START(total_size, fw_crc32, fw_version, window_size) ──→ [FW]
[App] ←─ OTA_START_ACK(result, resume_offset) ─────────── [FW]

[App] ─ OTA_DATA(seq=0, chunk) ──→ [FW]
[App] ─ OTA_DATA(seq=1, chunk) ──→ [FW]
   ... 连续发送 window_size 包 ...
[App] ←─ OTA_DATA_ACK(ack_seq=已收到的最大连续 seq, status) [FW]

[App] ←─ OTA_REBOOT_ACK ──→ [FW] → 进入 bootloader

8.5.2 关键设计决策

项决策理由
分块大小MTU=23 时 data=13B（帧头 4 + seq 2 + data 13 + crc 2 = 21 ≤ 20）；MTU=247 时 data=239B双端都按当前协商 MTU 动态计算，App 启动 OTA 前调 requestMtu(247) 并以实际返回值为准
窗口大小默认 8（可在 OTA_START 协商 1~32）窗口太小吞吐低；太大丢包重传成本高
ACK 粒度按窗口 ACK（非逐包），ack_seq 为已收到的最大连续包序号吞吐与可靠的平衡；丢包时 App 重发 [ack_seq+1, ...]
序号seq_u16_le 从 0 开始递增，不循环2^16 包 = 32 万包，远超固件体积；简化实现，无需处理 wrap-around
整包校验固件在 OTA_END 时对整包做 CRC32（而非逐包 CRC16 复算）双重校验：帧级 CRC16 防传输误码，文件级 CRC32 防重组错位
断点续传固件持久化「已写入 flash 的字节数」到 OTA_START_ACK 的 resume_offsetApp 重启 / 断链后重连即可续传，避免重传整包
防砖固件 bootloader 必须实现「双分区 + 回滚」——新固件启动后 30s 内未上报心跳 → 自动回滚旧分区App 端无法 100% 保证升级成功，固件侧兜底是硬要求

自测与文档自检

五道题覆盖这条链路的四个断点：ATT 事务、MTU、假连接、协议兼容。

  1. 为什么「订阅通知」也会引发 GATT 错误，而不是一个纯读操作？
    看答案

    订阅的本质是向 CCCD（0x2902）发一条 ATT Write Request，占用的就是写通道。它必须和业务写一起进命令队列串行，否则并发写会撞出 GATT 错误（见 2.3）。

  2. 固件支持 247 MTU，你按 244 字节分包，现场部分机型却一直丢包。最可能的原因？
    看答案

    MTU 协商是链路双方共同结果，iOS 由系统决定，Android 部分机型或旧固件会退回 23。协议必须按 20B 有效载荷设计，用协商返回值动态计算分块，而不是按最大值写死（见 8.1 / 8.5.2）。

  3. App 显示「已连接」，发命令却全部超时，且没有任何断线回调。怎么查？
    看答案

    典型「假连接」：连接参数协商失败后链路已死但双方都没触发 Supervision Timeout。用 adb shell dumpsys bluetooth_manager 看 LE Connection 段的 interval / latency / timeout，验证 interval × (latency+1) × 2 < timeout 是否成立。工程上靠心跳 + 3 次超时主动重连兜底（见 2.5）。

  4. 固件新增一个字段，App 老版本收到后解析全乱。协议该怎么设计才不出这种事？
    看答案

    新增字段只能追加在 payload 末尾；老版本按 LEN 截断读取即可忽略尾部。改变既有字段含义必须 bump 协议版本并新增 CMD，不修改旧 CMD 语义（见 8.8）。

  5. 为什么命令队列要做「单飞 + 超时 + 一次性重试」，而不是并发发送提速？
    看答案

    Write withResponse 是完整 ATT 事务，同一时刻只允许一个未完成写事务，并发只会制造 GATT 错误；且重试必须有上限，否则超时命令会在设备恢复后重复执行。吞吐靠 withoutResponse 通道与窗口 ACK，不靠并发写（见 2.3 / 6.9）。
