第 0 章 心智模型映射：从 iOS 到 Android 的概念翻译
================================================================================
这张表是全文索引，后续章节是对表项的展开。

| iOS 概念 | Android 对应 | 关键差异（必须记住） |
|---|---|---|
| Xcode + .xcodeproj | Android Studio + Gradle | 构建配置是代码(Kotlin DSL 文本)，不是 GUI 设置 |
| Info.plist | AndroidManifest.xml | 权限需运行时动态申请；Android 权限模型按 API 版本分多档演进 |
| Certificates(可吊销重发) | Keystore(.jks/.keystore) | 丢失不可恢复——丢了上传密钥且没接 Play 签名，等于永远失去该应用身份 |
| TestFlight | Play Console 内部/封闭测试轨道 | 新个人账号封闭测试需 12 名测试员连续参与 14 天才能申请正式发布 |
| App Store 审核数天 | Play 审核通常数小时~2 天 | 但 Play 事后政策扫描更严，违规可能下架甚至封号 |
| Universal Links(AASA) | App Links(assetlinks.json) | 机制同构：域名下放 JSON 验证；另有不需验证的 Deep Links(等同 scheme) |
| Keychain | Keystore + EncryptedSharedPreferences/DataStore | Android Keystore 存密钥而非直接存数据，落地需组合使用 |
| @objc 桥接/Method Channel | Platform Channel(Method/Event/BasicMessage) | Flutter 两侧都要写；Android 侧用 Kotlin |
| Instruments/Time Profiler | Android Studio Profiler/Perfetto | Android 有 ANR(主线程阻塞 5s+)这一 iOS 没有的独立崩溃类别 |
| Jetsam 杀后台 | LMK(Low Memory Killer)+Doze | Android 对后台更激进，厂商定制省电会额外杀进程(见 3.3) |
| Dynamic Type 字体缩放 | 字体缩放(fontScale)+显示尺寸 | sp 随用户字体缩放，布局必须可伸缩，dp 写死行高会出 bug |
| Launch Storyboard | SplashScreen API(Android 12+) | 系统强制冷启动画面，不能像 iOS 自定长启动动画 |
| CFBundleVersion | versionCode(整数递增) | 必须严格单调递增，无法回退；versionName 才是用户可见版本号 |
| ATS | networkSecurityConfig | 同构的明文传输管控，理解成本为零 |
| dSYM 符号化 | mapping.txt 归档 | 心智完全平移：不归档 = 该版本崩溃堆栈永久乱码 |
| 单一 App Store | Google Play + 国内数十家商店 | 国内无 GMS，推送/定位/支付全换方案，且需多渠道分包 |

【两个颠覆性认知：iOS 经验直接套用会出事故的地方】
1. 设备碎片化是产品级风险。iOS 只需适配 6~8 种屏幕；Android 面对上百种 DPI 组合
   + 十几代系统版本共存 + 三星/小米/华为等厂商深度定制 ROM。适配不是"做完就好"，
   是持续工程。
2. 签名密钥是不可再生资产。iOS 证书丢了重签即可；Android 上 App 正式签名密钥丢了，
   除非接入了 Google Play App Signing(托管正式密钥)，否则没有任何官方途径找回。
   这是入职第一天就该落库备份的事。

第 2 章 工程与构建层（A）
================================================================================

2.1 Gradle：Android 的"可编程 Xcode"
--------------------------------------------------------------------------------
iOS 开发者的最大不适应：Android 的一切构建设置都是文本代码。改签名、加依赖、配
渠道，都是改文件 + git 提交，没有 GUI 面板。

四个必懂文件：
  android/
  ├── settings.gradle(.kts)          # 声明哪些模块参与构建、插件仓库
  ├── build.gradle(.kts) [根]        # 全局插件版本(AGP/Kotlin 版本锁定在此)
  ├── gradle/wrapper/gradle-wrapper.properties  # Gradle 本体版本(分发版本)
  └── app/build.gradle.kts           # 模块级：applicationId、SDK 版本、签名、依赖

关键细节：
  - applicationId(如 com.company.app)≈ iOS Bundle ID，发布后永不可改，改了等于新 App。
  - 三个 SDK 版本号语义：
      minSdk     = 最低支持的系统版本，低于则无法安装
      targetSdk  = 你声明"已按此版本行为适配"，影响系统对你的行为限制
      compileSdk = 编译用的 API 版本，尽量最新
  - 【坑】targetSdk 不只是数字：设为 36，系统会强制启用 Android 16 的边到边显示、
    新版通知/权限等运行时行为——改 targetSdk = 一轮真回归测试，不是改配置了事。
  - 版本号规则：versionCode 整数递增(上传商店后不可降级)；versionName 是展示字符串。
  - Flutter 项目建议写 minSdk = flutter.minSdkVersion，跟随 Flutter 引擎要求。

2.2 依赖管理
--------------------------------------------------------------------------------
  - 依赖仓库：Google Maven + Maven Central(对标 CocoaPods trunk)；国内常加阿里云镜像。
  - 【坑】依赖冲突：两库共同依赖同一库不同版本时，Gradle 默认取最高版本，可能引发
    运行时 NoClassDefFoundError。用 ./gradlew app:dependencies 查看依赖树，冲突时用
    resolutionStrategy 强制统一(决策见 6 章末"依赖冲突排查决策图")。
  - AndroidX 是现代库统一前缀；见到 com.android.support:* 说明这库不要用。
  - 【iOS 习惯纠偏】iOS 依赖锁在 Podfile.lock；Android 对应 gradle.lockfile(默认不开)。
    建议开启 dependencyLocking，否则某三方库发个坏版本你的 CI 就炸。

2.3 构建变体：Build Types 与 Product Flavors
--------------------------------------------------------------------------------
  BuildTypes：debug / release(+ 自定义，如 staging)——对标 iOS Build Configuration
  Flavors：free / paid；或国内渠道 google / huawei / xiaomi / oppo…——对标多个 Target

两者笛卡尔积组合成变体。变体矩阵示意(2 flavor × 2 buildType = 4 变体)：

                    +-------------+--------------+
                    |   debug     |   release    |
   +----------------+-------------+--------------+
   | google flavor  | googleDebug | googleRelease|
   +----------------+-------------+--------------+
   | huawei flavor  | huaweiDebug | huaweiRelease|
   +----------------+-------------+--------------+
   再加一个 buildType(如 staging)即变 3×2=6；CI 必须显式指定要构建的变体，别全量跑。

  app/build.gradle.kts 示例：
    android {
        buildTypes {
            release {
                isMinifyEnabled = true          // 开 R8 混淆
                isShrinkResources = true        // 收缩未用资源
                proguardFiles(getDefaultProguardFile("proguard-android-optimize.txt"),
                              "proguard-rules.pro")
            }
        }
        flavorDimensions += "channel"
        productFlavors {
            create("google") { dimension="channel"; applicationIdSuffix=".g" }
            create("huawei") { dimension="channel" }
        }
    }
  【关键差异】iOS 不会在编译期改变代码逻辑结构；Android 的 flavor 可替换整个源码目录
  (src/huawei/java/… 优先于 src/main/)，可实现渠道级真差异，不只是配置差异。

2.4 当前推荐版本组合锚点【v2.0 新增】
--------------------------------------------------------------------------------
  原 v1.0 只写"AGP 8.x/Gradle 8.x"过虚。给出当期可即用锚点(复核时间：2026-11，以官方
  兼容表为最终准)：

    场景 A(追求主流，插件生态已适配)：
      Android Studio 最新稳定 + AGP 9.3.0 + Gradle 9.6.1 + JDK 17 + Kotlin 2.x
    场景 B(稳妥过渡，插件尚未适配 AGP 9)：
      AGP 8.13 + Gradle 8.13 + JDK 17 + Kotlin 2.3
    Flutter 项目：
      以 flutter create 生成的 android/ 脚手架为基线，跟随所用 Flutter 稳定版要求的
      AGP/Gradle；不要手工追最新 AGP，除非确认所用插件全部兼容。

  升级铁律(顺序不可乱，否则连环报错)：
      Android Studio → AGP → Gradle → JDK
  每次升级 Android Studio 后先跑一次构建——它可能顺手改坏这些版本号。
  速查：AGP 8.0 起强制 JDK 17；AGP 决定 Gradle 最低版本，Gradle 可高于最低但用官方推荐值。

3.1 屏幕适配
--------------------------------------------------------------------------------
单位体系(对照 iOS 的 pt)：
  - dp：密度无关像素，≈ iOS 的 pt。物理像素 = dp × 屏幕密度。
  - sp：随用户系统字体缩放倍数缩放的 dp——所有文字用 sp，行高/间距用 dp。用户把
    字体调到 1.3 倍时，写死 dp 的文字行会截断，这是 iOS 开发者最常见的适配 bug。
  - 密度桶：mdpi(1x)/hdpi(1.5x)/xhdpi(2x)/xxhdpi(3x)/xxxhdpi(4x)。图标按桶出图或
    统一用 Vector Drawable(XML 矢量，对标 PDF 矢量资产，强烈推荐，一份通吃全密度)。

布局响应性要求比 iOS 高：
  - 分屏(Android 7+)、自由窗口、折叠屏展开(大屏手机秒变平板)——Activity 可能随时
    改变尺寸，必须保证布局自适应，不能假设"竖屏全屏"。
  - android:resizeableActivity="true" 是默认预期；Flutter 应用整体自适应较好，但要
    处理键盘弹出(Android 键盘默认遮挡输入框，Flutter 中需设 resizeToAvoidBottomInset
    并实测各厂商键盘行为——国产 ROM 键盘高度上报经常不准，这是知名坑)。
  - 刘海屏：Android 用 WindowInsets 体系获取安全区(对标 env(safe-area-inset-*))。
    Flutter 的 SafeArea 默认可用，但边到边强制后需实测沉浸状态栏是否被内容穿透。

3.2 系统版本碎片化与 targetSdk 政策（硬性合规线 · 2026 口径）
--------------------------------------------------------------------------------
【v2.0 重要刷新】原 v1.0 写"target≥35、2025-08-31"已过期一年。2026 当期口径
(复核时间：2026-11)：
  - 2026-08-31 起：新应用 + 应用更新须 target ≥ Android 16(API 36)才能上架 Play；
    现有应用须 target ≥ API 35，才能在"系统版本高于其 target"的新设备上继续向新
    用户分发；target < 34 的应用只能装在系统 ≤ 其 target 的设备上。
  - 可申请延期至 2026-11-01(Play Console 内提交延期申请)。
  - Wear OS/Automotive target≥35；Android TV/XR target≥34。
  - Play Store 客户端最低系统已提到 Android 7，Android 6 及以下将无法访问商店。

| API | 关键分水岭 | 对开发者的关键影响 |
|---|---|---|
| 26 | (历史) | 通知必须走 NotificationChannel，否则静默丢失 |
| 29 | Scoped Storage | 不能随意读写公共存储，改用 MediaStore/SAF |
| 31 | exported 强制 | 含 intent-filter 的组件不显式声明 android:exported 直接装不上 |
| 33 | — | 通知权限改运行时申请(POST_NOTIFICATIONS)；引入 Photo Picker |
| 34 | — | 前台服务必须声明具体类型(camera/location/mediaPlayback…) |
| 35 | 2025 死线 | 边到边强制；16KB 内存页要求(已全面生效) |
| 36 | 2026-08-31 死线 | 新应用与更新须 target≥36；沿用并强化边到边/隐私收紧 |

16KB 内存页对齐(已生效，Flutter 项目必查)：target Android 15+ 且含原生 so 库的
应用必须按 16KB 页对齐，否则 Play 拒收。Flutter 引擎及含 native code 的插件(ffmpeg/
sqlite/加密库等)需升级到已对齐版本。验证：NDK 28+ 构建，或 llvm-readelf -l 检查 so 的
LOAD 段对齐值 ≥ 16384。Flutter 主线引擎已适配，风险在旧插件，集成前查 changelog。

【工作流建议】每年 8 月底是 Play 的 targetSdk 死线("最新系统版本发布 1 年内必须
target")，把"annual targetSdk 升级 + 完整回归"写进团队日历，预留延期申请兜底。

3.3 厂商碎片化（OEM ROM）——iOS 完全没有的维度
--------------------------------------------------------------------------------
同一份 APK 在小米、华为、三星上表现可能不同，因为厂商深度定制了系统行为：
| 厂商问题域 | 典型现象 | 应对 |
|---|---|---|
| 自启动管理 | 用户不手动允许"自启动"，推送进程被杀、收不到通知 | 引导到设置页开启；UI 做"保活指引"页 |
| 省电杀后台 | MIUI/EMUI 激进电池优化直接杀后台服务 | 申请电池优化白名单(商店审核会追问用途)；靠厂商推送通道兜底 |
| 推送通道 | 国内无 GMS → 没有 FCM | 华为 Push Kit、小米/OPPO/vivo Push、聚合 SDK(个推/极光)。iOS 一套 APNs 通吃在国内不存在 |
| 键盘与手势 | 各家键盘高度上报、全面屏手势区域不同 | 真机测试；键盘相关交互留余量 |
| 权限入口差异 | 自动跳转权限设置页在部分 ROM 失效 | 跳转失败降级为"请到设置>应用管理"文案引导 |

测试策略结论：真机矩阵至少覆盖——小米(MIUI/澎湃OS)、华为(新华为设备已是鸿蒙 NEXT，
不再兼容 APK，需单独评估，见 7.3 决策树)、OPPO/vivo、三星(国际标准行为参照)、一台
原生 Android(Pixel，验证无厂商干扰的标准行为)。模拟器只覆盖行为基线，省电/推送/键盘
问题只有真机能暴露。

3.4 系统行为差异速查
--------------------------------------------------------------------------------
  - 返回键/手势：iOS 没有系统返回概念。Android 有返回手势/按键，Flutter 用
    WillPopScope/PopScope 处理拦截(Android 14+ 预测性返回手势还要求提前声明)。
    App 内左滑返回 ≠ 系统返回，两套都要处理。
  - 深色模式：系统级切换，values-night/ 资源目录自动切换。Flutter 的
    MediaQuery.platformBrightness 可用，但原生页面、启动画面、通知图标要单独适配。
  - RTL：阿拉伯语等从右向左。Android 布局用 start/end 而非 left/right(Flutter 用
    EdgeInsetsDirectional)。接国际项目前确认需求。
  - 无障碍(接国际/合规项目补)：TalkBack 屏幕朗读；给可点击控件加 contentDescription、
    保证焦点顺序与最小点击区域(48dp)。Flutter 用 Semantics 控件标注。国内部分行业
    及海外应用商店已开始要求无障碍达标。
  - 图标：Adaptive Icon(前景层+背景层 XML)，不同启动器裁成圆/方/圆角方。给一层 PNG
    会被各家压变形。启动画面用 SplashScreen API，无法自定义展示时长。

3.5 量化适配基线【v2.0 新增】
--------------------------------------------------------------------------------
  让自检可量化，不靠"感觉还行"：
  - 字体缩放：必须在 fontScale = 1.0 / 1.3(部分 ROM 到 2.0)下无文字截断、无重叠。
  - 冷启动：目标 TTFD(Time to First Display/可交互) 中端机 < 2s，低端机 < 5s；
    Vitals 把冷启动 > 5s 计入"慢启动"占比，超 25% 需专项优化。
  - 边到边：Android 15+(target35/36)强制，所有页面无内容被状态栏/导航栏穿透。

第 4 章 运行时与系统集成层（C）

4.1 权限模型：一个权限的"三段式"认知 + 2026 最小化新规
--------------------------------------------------------------------------------
Android 权限 = Manifest 声明 + 运行时请求 + 用户可能永久拒绝，且行为随 API 漂移：
  - 安装时权限(normal 级)：INTERNET、VIBRATE 等，声明即得(对标 iOS 无感权限)。
  - 运行时权限(dangerous 级，API 23+)：相机、定位、麦克风、存储等。必须在交互时机
    请求(Flutter 用 permission_handler 统一封装)。
  - "不再询问"状态：用户两次拒绝后系统不再弹窗——必须检测
    shouldShowRequestPermissionRationale 引导去设置页。
  - 特殊权限：SYSTEM_ALERT_WINDOW(悬浮窗)、电池优化白名单等，要去系统设置页手动开。

近年"降级替换"趋势(Android 在向 iOS 隐私模型收敛)：精确/模糊定位二选一(API 31+)、
仅本次允许(对标 Allow Once)、照片部分授权(API 34)、Photo Picker(API 33+，无需权限)。

【v2.0 新增 2026 最小化新规(复核时间：2026-11)】
  - 通讯录：涉及邀请好友/分享内容/一次性请求联系人，target API 17+(按新政策)起必须
    改用 Contact Picker 并移除 READ_CONTACTS；仅通讯录管理/备份类可持续访问但需在
    Play Console 提交声明。生效窗口约 2026-10-27 起。
  - 位置：仅需一次性精确位置(发动态定位)必须用 Location Button 实现会话级访问；
    需持续定位(导航)可保留传统权限但需提交声明。
  - Data Safety 声明必须与 Manifest 权限、SDK 实际行为、网络请求、隐私政策四处一致，
    不一致直接审核失败。第三方 SDK 行为由开发者负责，需建立 SDK 审计机制。

4.2 组件模型：不要用"AppDelegate"的心智理解 Android
--------------------------------------------------------------------------------
iOS 是单入口单进程心智；Android 是四大组件，任何组件都可能被系统或别的 App 单独拉起：
  - Activity：一个可交互界面(≈ UIViewController)，多个 Activity 以栈(Task/Back Stack)
    管理，别的 App 可直接跳到你的某个 Activity。Flutter 通常只有一个 FlutterActivity，
    但接 SDK(支付/登录)时 SDK 会插自己的 Activity，返回栈行为就变复杂。
  - Service / 前台服务：后台任务载体。API 34 起必须声明类型且用途不符会被拒审。常驻
    后台服务(音乐/导航/运动)必须挂常驻通知——用户会看到"永远杀不掉的通知"，这是产品
    体验设计的一部分，不是纯技术细节。
  - BroadcastReceiver：系统事件监听(跨 App)。Android 13 起大部分系统广播需动态注册。
  - ContentProvider：跨 App 数据共享(相册、通讯录通过它读取)。

4.3 进程与后台：比 iOS 更激进的"被杀"世界
--------------------------------------------------------------------------------
  - LMK：内存不足按优先级杀进程(对标 Jetsam，但阈值更激进且厂商可改)。
  - Doze：设备静止/息屏后深度休眠，定时器、网络被系统批量延迟。精确闹钟需
    SCHEDULE_EXACT_ALARM 权限(API 31+ 需用户授权)。
  - 给 Flutter 开发者的实操结论：任何"离开 App 后台继续做事"(上传/下载/倒计时通知)
    都要走前台服务 + 常驻通知路线，纯 Dart Timer 在后台会被冻结。社区方案：
    flutter_background_service、workmanager(对标 BGTaskScheduler，但 Android 调度更不
    确定——WorkManager 只保证"最终执行"，不保证准时)。

4.4 深链
--------------------------------------------------------------------------------
  - Deep Link(自定义 scheme，myapp://page)：无验证，任何 App 都能声明同 scheme → 有
    劫持风险，仅作兜底。
  - App Links(https)：域名下托管 /.well-known/assetlinks.json(含应用签名 SHA-256 指纹)
    → 验证通过后 https 链接直接进 App。与 iOS AASA + Universal Links 机制完全同构。
    区别：iOS 需服务器返回 Content-Type: application/json 且有特定 HTTPS 要求；Android
    验证更宽松但失败时静默降级为"弹应用选择框"，排查时主动看 adb shell pm verify-app-links。
  - Flutter 处理：go_router 等声明 scheme/host，在 Activity onNewIntent 时把 intent 传给
    Flutter(默认已处理热启动 deep link，但冷启动的 initial link 要确认路由库版本支持)。

第 5 章 Flutter Android 侧集成层（D）
================================================================================

5.1 AndroidManifest：Flutter 项目的"信息中枢"
--------------------------------------------------------------------------------
Flutter 的 Android Manifest 在 android/app/src/main/AndroidManifest.xml。iOS 转 Flutter
最容易漏改的就是它(你习惯改 Info.plist)：
  - 权限声明(<uses-permission>)、应用显示名(android:label)、主题、android:exported；
  - 深链 intent-filter 挂在 FlutterActivity 上；
  - 【坑】release 包关掉调试网络配置残留；
  - 【坑】android:allowBackup="true" 默认开启——本地明文存的用户 token 会被备份到云端，
    敏感数据要么加密要么在 backup rules 里排除。

5.2 Platform Channel 实战要点
--------------------------------------------------------------------------------
Flutter 跨端通信三种通道：
| 通道类型 | 语义 | 典型场景 |
|---|---|---|
| MethodChannel | 请求-响应(一次调用一次返回) | 调用原生 SDK 单个方法 |
| EventChannel | 原生→Dart 持续数据流 | 传感器、电量、推送到达 |
| BasicMessageChannel | 双向自由消息 | 高频双向通信 |
易错细节：
  - 通道名两端必须完全一致(字符串硬编码易拼错，放常量文件)；
  - 数据仅支持可编解码类型(null/bool/num/String/List/Map/Uint8List)，自定义对象自己写
    Codec——iOS 侧转 JSON 字典最省事；
  - 主线程约定：Android 侧 MethodChannel 默认在主线程回调，耗时要切协程/线程再
    invokeMethod 回主线程；
  - 生命周期错配：页面销毁后 Dart 侧还有 invokeMethod → 原生侧判空防崩；原生侧在
    Activity 重建(旋转/进程恢复)后用旧 channel 回调 → Dart 已收不到，EventChannel 要在
    onListen/onCancel 中正确注册注销。

5.3 插件与原生依赖治理
--------------------------------------------------------------------------------
  - pubspec.yaml 引插件后，Android 侧真实依赖树在 android/build.gradle 生成产物里——
    插件本身还带 Gradle 依赖(对标：一个 CocoaPods 里嵌套了 SPM 依赖)。冲突时在
    app/build.gradle 用 configurations.all { resolutionStrategy } 强制版本。
  - 插件质量三查：①是否仍在维护(Flutter 升级后旧插件是最常见编译障碍)；②是否有原生
    依赖(涉及 16KB 对齐、so 冲突)；③是否要求升 minSdk(有的插件强制 minSdk 24+，会把
    整包最低版本抬上去——选型时就该看)。
  - 写自定义插件：Flutter 命令生成 Plugin 模板，Kotlin 写 Android 侧，FFI(dart:ffi)
    适合纯计算型原生调用(对标你熟悉的 C 互操作)。

5.4 Kotlin 最小生存集（iOS 开发者版）【v2.0 新增】
--------------------------------------------------------------------------------
读 SDK 源码、写 MethodChannel 不需要系统学 Kotlin，先掌握以下"够用子集"即可：
  - 空安全(最重要)：String 不可为 null；String? 可为 null。对应 iOS 的
    Swift 可选类型：String! 强解包 ≈ Swift 的 as! / !，慎用；安全调用 ?. 与 ?: (ELVIS)
    ≈ Swift 的 optional chaining ?? 默认值。
  - val / var：val ≈ let(不可变引用)，var ≈ var。优先 val。
  - 类型推断与 data class：data class 自动生成 equals/hashCode/copy，≈ Swift struct。
  - 扩展函数：fun String.xx() 给已有类加方法，≈ Swift extension。
  - 协程(必读，处理 MethodChannel 异步)：
      suspend fun = 挂起函数，≈ Swift async func；
      launch/async 在 CoroutineScope 里跑，≈ Swift Task/async let；
      切主线程用 withContext(Dispatchers.Main)，≈ DispatchQueue.main；
      切后台用 Dispatchers.IO。MethodChannel 耗时回调就包在 launch{ withContext(Main) }。
  - 高频坑：Kotlin 空安全和 Swift 语义相近，但平台类型(从 Java 回来的值)可能"看似非空
    实则可空"，NPE 多来自这里——和你在 Swift 里被隐式解包 Optional 崩过的是同一类问题。
学习路径建议：直接用 flutter create 生成的 Kotlin MainActivity 改起，遇到符号不懂查
Kotlin 官方"for people who work with Java/Swift"对照页，半天可上手 MethodChannel 级别。

6.1 签名体系（先弄清这个再打包）
--------------------------------------------------------------------------------
一套密钥，两个角色：
  - 上传密钥：你本地持有的 .jks + 密码，给上传到 Play 的包签名。
  - App 签名密钥：接入 Play App Signing 后由 Google 托管的"正式身份"，Google 用它
    重签后分发给用户。
【与 iOS 的核心差异】iOS 证书丢了重签即可(Apple 校验账号身份)；Android 一旦丢失正式
签名密钥，没有任何找回渠道，应用等于报废(用户无法升级，只能以新 applicationId 重新发)。

签名与分发流程示意(Play App Signing)：
   [本地上传密钥.jks] --签名--> [AAB 上传包] --> Play Console
                                                  |
                                          Google 用[App签名密钥]重签
                                                  |
                                          分发 APK/Split 给终端用户
   含义：上传密钥泄露可在 Console 重置(靠账号身份)；App签名密钥由 Google 托管，
   你丢了也能恢复分发身份；但若不接 App Signing，正式密钥丢=报废。

签名密钥管理制度（入职/立项第一天做）：
  1. keystore + 密码 + alias 入密码管理器/公司保险库，绝不进 git；
  2. CI 打包用环境变量/密钥管理服务注入(key.properties 只进 .gitignore)；
  3. 接入 Play App Signing，让 Google 托管正式密钥(上传密钥丢了可重置)；
  4. 记录 keystore 的 SHA-256 指纹——它同时用于 App Links 验证、第三方 SDK 平台
     (微信/高德等)注册；指纹变更要走全平台更新流程。

  标准签名配置写法(密码不进 git)：
    val keystoreProps = Properties().apply {
        val f = rootProject.file("key.properties")
        if (f.exists()) load(f.inputStream())
    }
    signingConfigs {
        create("release") {
            storeFile = keystoreProps["storeFile"]?.let { file(it) }
            storePassword = keystoreProps["storePassword"] as String?
            keyAlias = keystoreProps["keyAlias"] as String?
            keyPassword = keystoreProps["keyPassword"] as String?
        }
    }

6.2 AAB vs APK、ABI、16KB
--------------------------------------------------------------------------------
  - AAB(Android App Bundle)：Play 强制(2021-08 起新应用)，上传"中间格式"，Google 按
    设备动态生成按需分发 APK(Split APKs)，用户只下自己需要的资源和 ABI，包体降 30%+。
    flutter build appbundle 产出。AAB 不能直接装手机测试，本地用 bundletool 转真 APK。
  - 国内商店不收 AAB，只收通用 APK——国内项目构建链双轨：Play 走 AAB，国内各商店走
    flutter build apk --split-per-abi 或 fat APK。
  - ABI：armeabi-v7a(32 位老设备)/ arm64-v8a(主流 64 位)/ x86_64(模拟器)。Play 要求
    含 arm64；--split-per-abi 拆分后单包体积减半以上。
  - 16KB 对齐(见 3.2)：含原生 so 的 target 35/36 应用 Play 硬门槛，上传前自查。

6.3 构建优化（release 包质量三件事）
--------------------------------------------------------------------------------
  1. R8 混淆与收缩：isMinifyEnabled + isShrinkResources。Flutter 引擎与插件自带 consumer
     rules，但反射调用的原生 SDK(支付/推送/序列化库)需手动 keep 规则，否则 release
     运行时闪退而 debug 正常——【经典坑】"debug 好好的，release 一启动就崩"，九成是
     混淆规则没写。
  2. 符号上传：混淆后崩溃堆栈乱码(a.b.c)，要把 R8 生成的 mapping.txt 归档并上传
     Crashlytics/Sentry 才能还原堆栈。iOS 的 dSYM 心智完全平移。每个 versionCode 的
     mapping 都要留档，丢失 = 该版本崩溃无法解读。
  3. 启动性能：Flutter 冷启动白屏常见于低端机与国产 ROM，手段：启动画面适配 + Dart 主
     隔离预初始化 + 关注 Android Vitals 的 TTFD 指标(目标见 3.5)。

6.4 国内多渠道打包
--------------------------------------------------------------------------------
  - 渠道维度用 flavor 或 walle(美团方案，基于 V2 签名写渠道信息，秒级出包)实现；
  - 每个渠道统计 SDK 初始化开关 + 各商店隐私声明差异，在 flavor 源目录隔离；
  - 【坑】多渠道 × 多 buildType 变体数量爆炸(4 渠道 × 2 = 8 变体)，CI 显式指定变体。

  依赖冲突排查决策图：
    运行报 NoClassDefFoundError / NoSuchMethodError
            |
    ./gradlew app:dependencies 看依赖树
            |
    同一库出现多版本？ --否--> 排查 R8 keep / 混淆(见 6.3)
            |是
    确认你真正需要的版本
            |
    在 app/build.gradle 用 resolutionStrategy.force 锁定
            |
    clean 后重跑 dependencies 验证只剩一个版本 → 真机回归

7.1 Google Play 发布全流程（对标 TestFlight + App Store）
--------------------------------------------------------------------------------
轨道结构(对标 TestFlight 分组)：
  内部测试(Internal，≤100 人，秒级分发)→ 封闭测试(Closed，邮件列表/Google Group)
  → 开放测试(Open，可从商店页加入)→ 正式版(Production，支持分阶段放量)

放量漏斗示意(正式发布用 staged rollout)：
   Production 发布
        |
     [ 1% ]  观察 12~24h：崩溃率 / ANR / Vitals
        |  异常 → 暂停放量(Hold rollout)，发更高 versionCode 修复
     [ 10% ] 观察
        |
     [ 50% ]
        |
     [ 100% ]
   Play 的放量可随时暂停、不可回退已装版本——比 iOS 更细粒度的发布控制，默认开启。

硬性合规清单（2026 口径，逐项核对；复核时间：2026-11）：
  [ ] targetSdk ≥ 36(2026-08-31 起新应用与更新要求；每年 8 月底滚动上调)；
  [ ] 现有应用若 target < 35，将无法在高系统新设备上向新用户分发；
  [ ] 含原生 so 的应用已支持 16KB 页对齐(已强制)；
  [ ] AAB 格式上传；接入 Play App Signing；
  [ ] 开发者身份验证已完成(2026 年起强制：法定姓名/地址/邮箱/电话，部分国家先行强制，
      未验证开发者签名的应用无法在认证设备安装/更新；2026-09-30 前未完成登记可能被全球下架)；
  [ ] 新个人开发者账号：正式版发布权限前须完成封闭测试——至少 12 名测试人员连续
      参与 14 天(适用 2023-11-13 后创建的个人账号；企业账号豁免)。注意 Google 审的是
      "真实性+连续性"，不是凑邮箱名单：测试者须通过测试链接 opt-in 并保持 14 天不中断，
      中途退出/人数不足/无真实反馈都会导致补测。提前 3 周规划，与开发并行启动；
  [ ] Data Safety 表单与实际行为、Manifest 权限、隐私政策四处一致(不一致=审核失败)；
  [ ] 隐私政策 URL 公网可访问；内容分级问卷、目标受众(含儿童触发更严政策)、广告声明；
  [ ] 2026 政策：核心功能为匿名聊天/随机匹配的应用须屏蔽未成年人 + 举报入口 +
      儿童安全联系人(2026-08-26 起)；
  [ ] 商店素材：图标 512×512、功能图 1024×500、各机型截图。
  补充：收入分成(2026-07-22 起美国区)标准 IAP 降至 20%、订阅 10%；年收入 <$100 万走
  10% 基础费率——定价测算时按新费率(此条随地区/政策变动，签约前核 Play Billing 文档)。

审核与放量：Play 初审通常数小时~2 天，但事后机器+人工扫描持续进行；上架后立即做
Pre-launch Report(自动真机测试)与 Android Vitals 基线确认。

7.2 国内应用商店发布（iOS 经验零平移的新领域）
--------------------------------------------------------------------------------
前置资质(比技术更容易卡流程)：
  1. 软件著作权(软著)：多数商店上架必备，申请周期数周，提前办；
  2. ICP 备案 / App 备案：2023 年起工信部要求 App 备案，无备案号商店直接拒收——国内
     发布硬门槛，走企业主体 + 服务器在国内；
  3. 《隐私政策》符合《个人信息保护法》《网络安全法》：权限用途逐条说明、SDK 清单披露；
  4. 特定行业额外资质：金融牌照、医疗审批、教育备案等；
  5. 各家商店(华为/小米/OPPO/vivo/应用宝…)各自注册开发者账号(企业账号需营业执照+对公
     验证)，每家审核标准、素材尺寸、更新说明规范都不同，首次全流程预留 2~4 周。
技术差异：无 GMS → 推送用厂商通道/聚合 SDK；支付接微信/支付宝(非 IAP 垄断，虚拟商品也
可走第三方支付，与 iOS 抽成规则完全不同)；地图/定位换高德/百度；商店对权限滥用、强制
索权、启动弹窗极敏感——"启动即弹权限"是高频驳回项，权限请求要跟功能场景绑定。
多渠道发布节奏：主版本统一日发布，但各商店审核时长不一(1~7 天)，用 CI 出渠道包 +
各商店后台分别提审，建立渠道发布状态表跟踪。

7.3 版本与灰度策略 + 鸿蒙 NEXT 出包决策树【v2.0 补决策树】
--------------------------------------------------------------------------------
  - 版本号策略：versionCode 用规则化数字(如 MMmmpp 或构建流水号)，保证单调且可追溯；
  - 灰度：Play 用分阶段放量；国内商店多数支持"按比例发布"(华为/小米)，部分只能全量——
    以最慢的商店为准规划回滚预案；
  - 回滚：Android 不能撤回已装版本，只能发更高 versionCode 修复——所以"发版前真机冒烟
    + 灰度观察 24h Vitals"是纪律不是建议。

  鸿蒙 NEXT 出包决策树(华为设备已不再兼容 APK)：
      目标用户里华为存量机型占比是否显著(如 >15%)？
            |
        否 --┤--> 暂不出鸿蒙版，监控华为用户流失/差评，季度复评
            |
        是 --┴--> 是否有预算与人力做独立 ArkTS 工程？(鸿蒙 NEXT 不跑 APK/AOSP)
                    |
                否 --┤--> 仅覆盖"仍带 AOSP 的旧华为"，新机型用户走 Web/小程序兜底
                    |
                是 --┴--> 单独立项鸿蒙原生(ArkTS/ArkUI，非 Flutter，需评估重写成本)；
                          Flutter 社区鸿蒙版仅适配特定引擎，先验证关键插件可用性再决策。

第 8 章 质量与运维层（G）
================================================================================

8.1 监控三件套 + 量化红线【v2.0 补阈值】
--------------------------------------------------------------------------------
| 维度 | 工具 | 与 iOS 的差异 |
|---|---|---|
| 崩溃 | Crashlytics / Sentry | 多了 ANR 类别(主线程 5s 无响应)——iOS 无此独立类别；ANR 常由 Flutter 主隔离阻塞或原生主线程 IO 引起 |
| 性能基线 | Android Vitals(Play 内置，免费) | 直接影响商店搜索排名(崩溃/ANR 过高会被降权甚至警示)——Play 特有的运营级惩罚 |
| 自定义性能 | Firebase Performance / 自建 | 关注冷启动(TTFD)、页面帧率 |

量化红线(Vitals"差"判定参考，复核时间：2026-11，以后台当期口径为准)：
  - 崩溃率(bad battery 口径之外的用户会话崩溃率)：> 1.09% 判"差"，红线目标 < 1%；
  - ANR 率：> 0.47% 判"差"，目标 < 0.47%(越低越好，业界良好线约 0.1%)；
  - 危险 API 误用 / 卡死帧等各有专项阈值，在 Play Console 的 Vitals"核心指标"页对照；
  - 冷启动占比超 25% 或 TTFD 中端机 > 2s 触发自检(见 3.5)。
  → 自检清单用这些数字设 KPI，而不是"尽量低"。

ANR 排查必备技能：会读 /data/anr/ traces(或 Play Console 下载聚合 ANR 堆栈)——主线程
在等锁/等 binder/做 IO 是三大常见原因。

8.2 兼容性测试矩阵（最低配置建议）
--------------------------------------------------------------------------------
  - 真机 5 台：Pixel(标准行为)+ 三星(国际市占第一)+ 小米 + 华为/荣耀 + OPPO/vivo(任选)；
  - 系统版本：最低支持版本 1 台 + 最新正式版 1 台；
  - 状态矩阵：深色开/关、字体缩放 1.0/1.3、分屏、弱网(飞行模式切换)、权限全拒/全给、
    进程被杀后恢复(开发者选项"不保留活动"打开后回归一遍，模拟激进后台)；
  - Play Console 设备目录可查用户真实机型分布，按用户分布配测试机，不按情怀配。

8.3 Flutter 特有的质量项
--------------------------------------------------------------------------------
  - Dart 主隔离阻塞同样引发 ANR(手势事件在平台线程分发到 Dart 后被阻塞)——耗时计算用
    compute()/Isolate.run；
  - 插件升级后必须回归原生侧行为(权限文案、通知、deeplink)，因为插件可能含原生代码变更；
  - 崩溃日志两套体系并存：Dart 异常与原生崩溃(tombstone/NDK crash)，Crashlytics 两边都要
    配(Flutter 侧 FlutterError.onError + PlatformDispatcher.onError 接入)。

第 9 章 自动化测试与 CI/CD（H）【v2.0 新增章】
================================================================================
原 v1.0 只有"真机矩阵"，缺自动化测试与成型的 CI/CD 方案，这是工程团队刚需，补之。

9.1 测试金字塔
--------------------------------------------------------------------------------
              /  UI / E2E  \        少量、慢、脆：关键业务流
             /  Instrumentation \    中等：真机/模拟器组件、权限、深链
            /____ Unit(JVM) ______\  大量、快、稳：纯逻辑、ViewModel、Codec

  三层 + 云测：
  - 单元测试(JVM)：JUnit4/5 + MockK(对标 XCTest + OCMock)。纯 Kotlin 逻辑、序列化、
    工具类放这里，跑在 host JVM，秒级。Flutter 侧对应 flutter test。
  - Instrumentation 测试：AndroidX Test(Espresso 操作 View，Espresso-Intents 测深链)。
    需要设备/模拟器，覆盖权限流、Activity 生命周期、深链冷启动。Flutter 侧对应
    integration_test(能驱动到真实平台通道)。
  - UI 测试：Espresso / Compose test(若有原生 Compose 页)。
  - 云测/真机农场：Firebase Test Lab(Google 设备矩阵，跑 instrumentation，出兼容性报告)，
    替代自建大设备库；Play Console 的 Pre-launch Report 是免费的入门云测。
  Flutter 团队落地建议：纯逻辑用 flutter test + 原生单元测试；关键"跨平台通道"路径用
  integration_test 跑真机；上架前用 Firebase Test Lab 扫一遍机型兼容性。别追求满覆盖，
  优先覆盖第 12 章高频坑清单对应的路径。

9.2 CI/CD 流水线骨架
--------------------------------------------------------------------------------
  两条主流路线，按团队栈选其一：
  - Fastlane：跨 Android/iOS 统一。lane 覆盖 build(出多渠道包)→ sign(注入 keystore)→
    deliver(上传 Play / 各商店)。签名密钥用 CI 环境变量或 secret manager 注入。
  - GitHub Actions / GitLab CI：用 setup-java + gradle action 跑构建，产物上传 release。

  一条最小可用流水线骨架(build → test → sign → upload)：
    1) 触发：tag / 手动；
    2) 环境：checkout → setup JDK 17 → cache gradle；
    3) 静态/单测：./gradlew test lint  ；flutter test ；
    4) 构建：flutter build appbundle(Play) + flutter build apk --split-per-abi(国内)；
       版本号从流水号注入 versionCode，保证单调；
    5) 签名：从 secret 还原 key.properties / keystore(不落 git)；
    6) 归档产物：mapping.txt 按 versionCode 归档(供符号化)；
    7) 上传：Play 走 fastlane supply / Google Play Delivery 上传到内部测试轨道；
       国内各渠道包走人工或各家上架 API，更新渠道发布状态表；
    8) 冒烟门：内部测试轨道真机冒烟 + 灰度放量观察 Vitals 后再推进放量。
  纪律：CI 必须显式指定要构建的变体(见 6.4)，禁止全量笛卡尔积；release 签名密钥只走
  secret，绝不进仓库与日志。

第 10 章 iOS→Android 过渡期调试手册（I）【v2.0 新增章】
================================================================================
iOS 转 Android 的"肌肉记忆"速查表，把零散出现的调试技能汇总成章。

10.1 adb / logcat 肌肉记忆（对标你的 Xcode Console / Instruments）
--------------------------------------------------------------------------------
  adb devices                     # 看连了哪些设备(对标 Xcode 设备列表)
  adb -s <serial> install -r app.apk    # 装/覆盖安装
  adb shell pm list packages | grep com.  # 按包名找应用(对标找 Bundle ID)
  adb logcat -s Flutter           # 只看 Flutter 打点(print 的输出去这里找)
  adb logcat *:E                  # 只看 Error 级(定位崩溃前的报错)
  adb logcat > crash.log          # 全量落文件，配合复现时间戳回看
  adb shell dumpsys activity activities   # 看当前 Activity 栈(理解返回栈关键)
  adb shell dumpsys meminfo <pkg> # 看内存(对标 Memory Graph 数值)
  adb shell dumpsys gfxinfo <pkg> # 看掉帧(对标 Core Animation 掉帧)
  adb bugreport bugreport.zip     # 大杂烩诊断包(ANR/省电/广播都进这里)
  adb shell pm verify-app-links   # 验证 App Links 是否真的生效(见 4.4)
  Flutter 专项：flutter run -v 看完整构建原生日志；flutter devices / flutter doctor -v。

10.2 开发者选项与抓包工具
--------------------------------------------------------------------------------
  开发者选项(回归必开，对标 iOS 的开发者菜单)：
   - "不保留活动"：离开即销毁 Activity，模拟激进后台杀进程——深链/状态恢复必测；
   - "指针位置/显示布局边界"：定位布局溢出、dp/sp 截断问题；
   - 强制 RTL 布局：验证阿拉伯语镜像(见 3.4)；
   - "关闭动画(窗口/过渡/动画时长 0)"：自动化测试与快速复现。
  网络抓包(对标 iOS 的 Proxyman/Charles)：
   - 设备端代理型：Charles / mitmproxy(手机设代理 + 装 CA 证书)；
   - App 内嵌型：Chucker / Stetho(Android 库，对标 iOS 里的网络日志面板)，release 别打进；
   - Android 9+ 默认禁明文，抓 HTTP 需在 networkSecurityConfig 临时放行(见第 11 章)；
   - 抓 HTTPS 记得 release 包默认不信任用户安装的 CA，需 debug 构建或网络安全配置放行。

10.3 iOS→Android 排障速查（症状→第一步）
--------------------------------------------------------------------------------
  - 装了没反应/找不到入口 → 检查 launcher activity 的 intent-filter 与 exported；
  - release 崩 debug 好 → 先看 mapping.txt 是否缺 keep 规则(见 6.3)，再 logcat -s AndroidRuntime；
  - 通知不响 → NotificationChannel 是否建(API 26+)、通知权限是否申请(API 33+)；
  - 收不到推送 → 国内厂商通道是否配、自启动/电池白名单(见 3.3)；
  - 深链冷启动打不开 → assetlinks.json 指纹是否匹配 + adb shell pm verify-app-links；
  - 布局在放大字体下截断 → 文字是否误用 dp 写死(见 3.1)，调 fontScale 复现；
  - 主界面卡住不动 → 主隔离阻塞导致 ANR，用 compute/Isolate 挪耗时(见 8.3)。

第 11 章 安全层（J）
================================================================================

11.1 网络安全配置与明文传输
--------------------------------------------------------------------------------
  Android 9+ 默认禁 cleartext HTTP；要用 HTTP 必须在 networkSecurityConfig 显式放行——
  这是 iOS ATS 的同构物，理解成本为零。抓包调试需临时放行见 10.2。

11.2 数据存储与组件暴露
--------------------------------------------------------------------------------
  - 组件暴露：exported="true" 的 Activity/Service 可被任意第三方 App 调起——对标 iOS
    URL Scheme 全开放，但 Android 可调用组件更多。敏感页面加签名校验或设 exported="false"。
  - 数据存储：敏感数据用 EncryptedSharedPreferences / flutter_secure_storage(底层 Keystore)；
    allowBackup 排除敏感文件；调试残留(debuggable、日志、测试后门)在 release 中关闭。
  - 密钥安全：任何硬编码在客户端的 secret 都视为公开(与 iOS 同理)；高德/微信等平台的
    App 签名绑定(用 keystore 指纹绑定 SDK)是 Android 防冒用主要手段——这就是为什么
    keystore 指纹变更要走全平台更新流程，也反过来要求 keystore 终身不变。

11.3 加固与反逆向（含代码透明性红线）
--------------------------------------------------------------------------------
  - 国内发布惯例接入加固(腾讯乐固/360/爱加密等)，防 dex 反编译与二次打包；Play 侧用
    R8 + Play Integrity API(对标 iOS DeviceCheck/App Attest)防重打包与设备伪造。
  - 【v2.0 新增 2026 合规红线】Play 禁止动态下载/执行外部可执行代码(DEX/JAR/SO)；
    加固方案不得破坏代码透明性(Code Transparency)——即不能改变原始 DEX 与原生库的哈希值；
    须兼容 Play Integrity 与 Play Protect 认证；用 Play App Signing 时，加固后签名需与
    控制台记录一致。选加固供应商时先确认它满足 Code Transparency，否则会被 Play 拒/下架。

第 12 章 高频坑清单（iOS 开发者视角，按事故概率排序）
================================================================================
 1. release 包闪退 debug 正常 → R8 混淆缺 keep 规则(第 6.3)；
 2. targetSdk 升级后通知/前台服务/边到边行为全变 → 把 targetSdk 升级当版本发布做，
    跑完整回归(第 3.2)；本期务必升到 target36；
 3. 国产 ROM 收不到推送/后台被杀 → 没接厂商推送通道 + 未引导自启动(第 3.3)；
 4. 发布后因 minSdk/权限被商店拒 → 提审前用第 14 章清单核对(第 7 章)；
 5. 字体缩放后布局崩坏 → 文字行高用 dp 写死(第 3.1)；
 6. 深链冷启动失效 → initial link 未处理或 assetlinks.json 指纹不匹配(第 4.4)；
 7. Flutter/AGP/Gradle 版本矩阵升级连环报错 → 按官方兼容表顺序升，锚点见 2.4；
 8. 上传 versionCode 重复被拒 → CI 固定从流水号取 versionCode(第 6.4 / 7.3)；
 9. 混淆后 mapping 丢失，崩溃无法解读 → mapping 随 versionCode 归档(第 6.3)；
10. keystore 存在个人电脑里 → 立即按第 6.1 制度迁移；
11. Android 15/16 上页面被状态栏穿透 → 边到边强制后未适配 WindowInsets(第 3.1)；
12. 含旧 native 插件被 Play 拒收 → 16KB 对齐(第 3.2)；
13. 新个人号后台能传包但永远发不了正式版 → 封闭测试 12 人×14 天未达标(真实 opt-in，
    非凑邮箱)(第 7.1)；
14. 通讯录/定位申请被新版审核驳回 → 未改用 Contact Picker / Location Button(第 4.1)；
15. 加固后上架被拒/下架 → 加固破坏了 Code Transparency(哈希被改)(第 11.3)。

  以上为"即用锚点"，不是永久真理；每季度按官方兼容表复核一次。
