Chapter 01

整体架构

L1｜四层分工：客户端 → Nginx → NestJS 业务层 → 四个各司其职的存储中间件

  • MySQL：用户、会话、消息、任务、权限、文档元信息、工具调用记录——结构化、需事务、联表、索引
  • Redis：不存核心持久业务，只做高速临时数据（队列场景必须开 AOF 持久化）
  • MinIO：只存原始文件（pdf / md / 图片），文件元信息落 MySQL
  • Qdrant：只存切片文本、embedding 向量、切片 id、关联 document_meta.id，以及父子分块的父块原文 payload；原始文档不进向量库

Chapter 03

数据库设计规范（MySQL + Prisma）

L1｜六张核心表贴着 AI Agent / RAG 业务长，索引与事务是练手重点

  • user：账号、密码（bcrypt）、角色、refresh token 哈希（支持登出吊销）、创建时间
  • chat_session / chat_message：会话与消息，消息含角色、内容、token 消耗、工具调用记录
  • agent_task：主 Agent 派发的子任务、状态、结果、重试次数
  • document_meta：文件名、MinIO 路径、类型、上传人、切片状态、向量入库状态
  • tool_record：function name、入参、返回、是否成功、错误信息（审计与排错）
展开细节：四项练习重点（Migration / 索引 / 事务 / 分表）
  • Prisma Migration 管理表结构变更——企业标准，代替手写 SQL 改表
  • 索引设计：会话查询、用户查询、时间范围查询，用 EXPLAIN 分析慢查询
  • 事务：Agent 多步操作、文档入库（元数据写入 + 文件上传 + 切片向量入库，失败需回滚）
  • 分表练习（进阶）：chat_message 量大后按 sessionId 哈希分表，推荐先做 MySQL 原生 PARTITION（见阶段 9）
展开实战：把「索引设计」变成可执行动作 
-- 1. 打开慢查询日志（练手环境把阈值放低，才观察得到）
SET GLOBAL slow_query_log = 'ON';
SET GLOBAL long_query_time = 0.2;

-- 2. 看执行计划：重点看 type / key / rows / Extra 四列
EXPLAIN SELECT * FROM ChatMessage
WHERE sessionId = 'ckxxxx' ORDER BY createdAt DESC LIMIT 20;

-- 3. type=ALL 是全表扫描；key=NULL 说明没走索引；
--    Extra 里出现 Using filesort 说明排序没被索引覆盖
SHOW INDEX FROM ChatMessage;
  • 联合索引遵循最左前缀：@@index([sessionId, status]) 能命中 WHERE sessionId=? 和 WHERE sessionId=? AND status=?，但命中不了只按 status 过滤的查询
  • 「等值列在前、排序列在后」：建成 (sessionId, createdAt)，ORDER BY createdAt DESC LIMIT 20 才能免排序
  • 连接池打满的典型症状：请求偶发超时，MySQL 侧 SHOW PROCESSLIST 里一堆 Sleep——先查是不是事务没关，再考虑调 connection_limit
  • 事务里绝不夹外部 HTTP 调用（例如把 embedding 请求放进 $transaction），否则一个慢请求就占住一个连接

Redis｜只做高速临时数据，队列场景有持久化红线

  • 接口缓存：高频 RAG 检索结果缓存，减少 Qdrant 查询（穿透 / 击穿 / 雪崩三件套防御见阶段 9）
  • 分布式锁：防同一 Agent 任务并发重复执行
  • 限流：接口请求限流
  • BullMQ 任务队列：文档解析、切片、embedding 生成、本地大模型推理等长任务，避免 HTTP 超时
  • 临时会话缓存（可选）

持久化红线：队列场景必须开 AOF（appendonly yes），否则容器重启丢任务；配 maxmemory 512mb + maxmemory-policy noeviction——队列数据绝不能被驱逐。

MinIO 与 Qdrant｜文件与向量各守边界，不与业务库混

  • MinIO：文件不直接存 MySQL；MySQL 只存文件元数据和 MinIO 对象 key
  • 支持分片上传（大文档）、访问签名 URL；练习权限策略、文件过期、文件删除
  • Qdrant：只存切片、向量、切片 id、关联 document_meta.id，payload 额外存父块原文
  • 检索拿到切片后，按需回查 MySQL 文档元信息，或直接返回 payload 中的父块原文
  • 独立服务、不与业务库混，方便横向扩容（企业 AI 项目标准拆分）
展开细节：2G 内存机器的向量库省内存做法

练手 2G 内存机器：容器限内存 + 开 int8 标量量化，是 2025+ 向量库省内存的常规操作。

Chapter 04

业务核心流程（3 条主线）

点击步骤节点可高亮当前所处环节，便于对照代码逐段实现。

  1. 前端提交用户问题 + sessionIdFlutter / Web 发起请求
  2. Controller 接收请求，JWT 鉴权Nest 层只做参数接收与校验
  3. Service 组装系统提示词 + 历史消息从 MySQL 读取 chat_message，游标分页见阶段 3
  4. 请求 LLMDeepSeek / 千问 API，OpenAI 兼容协议统一接入
  5. LLM 返回 Function Calling 结构（工具名 + 参数）
    1. 分支 A：不需要调用工具 → 直接把回答入库，返回前端
    2. 5.1 工具调度器校验函数、参数（防幻觉参数）
    3. 5.2 注册工具：rag_search、read_codemap、create_agent_subtask 等（对齐 MCP）
    4. 5.3 执行工具逻辑（如 rag_search 调用 Qdrant 检索）
    5. 5.4 工具执行结果写入 tool_record 表
    6. 5.5 把工具返回结果塞回对话上下文，再次交给 LLM
  6. LLM 整合结果，生成最终回答
  7. 新消息写入 chat_message
  8. 返回给前端

实战建议（重要）

5.1 / 5.5 / 防死循环这三件事，2026 年不要手写循环——用 Vercel AI SDK 5 的内置多步工具循环：工具 schema 用 zod 定义即自动校验参数；每步 toolCall / toolResult 自动回填上下文；stopWhen: stepCountIs(8) 一行实现轮次上限。完整代码骨架见阶段 4。

练手考点

  • 控制最大 FC 轮次，防止死循环
  • 上下文截断、摘要
  • 异常捕获（工具调用失败重试）
  • 写操作工具二次确认：工具返回 { needConfirm: true, dryRunResult }，前端确认后携 confirmationId 二次调用——把「禁止模型直接执行」从口号变成协议
  1. 用户上传文档（md / pdf）
  2. Nest 接收，上传文件到 MinIO
  3. document_meta 新增一条记录，状态 = 待解析
  4. 投递任务到 BullMQ 队列jobId = doc:{documentId} 幂等键，见阶段 7
  5. Worker 消费任务
    1. 5.1 从 MinIO 下载文件
    2. 5.2 文档解析、清洗、切片（分块策略见阶段 5）
    3. 5.3 调用 Embedding 模型生成向量（Qwen3-Embedding，见阶段 5）
    4. 5.4 向量写入 Qdrant，绑定 document_meta.id，payload 存父块原文
    5. 5.5 更新 document_meta 状态 = 已入库
  6. 前端通过 SSE 获取任务进度worker 内 updateProgress，见阶段 7

为什么必须异步

文档解析、embedding 很慢，HTTP 同步请求极易超时——企业长任务的标准方案就是投递到队列，由 worker 消费，进度经 SSE 回推。

  1. 用户复杂需求交给主 Agent
  2. 主 Agent 通过 FC 判断是否拆分任务
  3. 如需拆分，调用工具 call_sub_agent(subAgentName, task)
  4. 子 Agent 独立执行自己的任务子 Agent 同样可以拥有自己的工具、RAG 检索
  5. 子 Agent 结果返回主 Agent回传前先摘要压缩，防上下文爆炸
  6. 主 Agent 汇总所有子任务输出，生成最终答案
  7. 所有任务、子任务记录存入 agent_task

实战建议

主从调度用 BullMQ FlowProducer 父子任务 DAG 落地（父任务等全部子任务完成后自动触发汇总 job），与 agent_task 状态机天然对齐，比手写「轮询子任务状态」干净一个量级。代码见阶段 6。

Chapter 07

Prisma 详细使用指南

L1｜Prisma 是 TypeScript 优先的现代 ORM，三大组成：schema 单源真相 + Migrate 版本迁移 + Client 类型安全查询

  • schema.prisma：数据模型单源真相
  • Prisma Migrate：数据库版本迁移，替代手写 SQL 改表（企业标准）
  • Prisma Client：自动生成类型安全查询 SDK，在 Nest Service 读写数据库
  • 替代 TypeORM / Sequelize；国内新项目、Nest 后端广泛使用，特点是强类型、自动生成 TS 类型、Migration 版本化管理表结构
  • 两个最容易翻车的点：新 generator 强制要求显式 output；PrismaService 必须实现 onModuleDestroy 并配 enableShutdownHooks()

7.1 schema.prisma（MySQL 版，可直接用于项目）

⚠️ 高频报错预警：2025 年起的新 generator prisma-client 强制要求显式 output 路径，且生成代码不再默认放 node_modules/.prisma，需在 tsconfig paths 中注册；照抄网上旧教程的写法会在 prisma generate 直接失败。

⚠️ 新手最常漏的一步：优雅停机。只写 $connect() 不写 $disconnect()、main.ts 里没有 enableShutdownHooks()——容器收到 SIGTERM 时进程被强杀，事务中断、连接不释放。

import { Injectable, OnModuleInit, OnModuleDestroy } from '@nestjs/common';
import { PrismaClient } from './generated/client';

@Injectable()
export class PrismaService
  extends PrismaClient
  implements OnModuleInit, OnModuleDestroy
{
  async onModuleInit() {
    await this.$connect();
  }

  async onModuleDestroy() {
    await this.$disconnect();   // 容器 SIGTERM 时释放连接池
  }
}

阶段目标：完成文档入库 + 检索闭环，并建立可度量的检索质量评测——不止「入库四步」，还要做质量工程（2024-2025 分水岭）

  • Embedding 选型：Qwen3-Embedding 系列（2025-06 发布），0.6B / 4B / 8B 三档，embedding + rerank 双任务，多语言（含中文）榜单开源 SOTA；国内 API 侧阿里百炼 / 硅基流动均提供托管端点，自部署可选 0.6B（2G 内存需配合量化）。选型要点：检索与 rerank 同族模型，分数空间一致

阶段目标：文档解析 / embedding / 子 Agent 任务全面异步化，达到生产级队列纪律

  • 幂等是队列的第一公民：job 指定 jobId = doc:{documentId}，重复投递直接复用既有 job——重复上传、worker 崩溃重投都不会重复解析（重复解析 = 重复扣 embedding 费用）
  • 重试策略工程化：attempts: 3 + 指数退避；区分可重试错误（网络超时）与不可重试错误（文件损坏，直接 failed）
  • 可观测：挂 Bull Board（@bull-board/express 或 Nest 集成包），浏览器直观看等待 / 活跃 / 失败队列——练手项目最划算的可视化投入
  • 进度上报对齐阶段 3 的 SSE：worker 内 await job.updateProgress(45)，SSE 端订阅 BullMQ 事件转发前端，替代轮询

await queue.add('parse-document',
  { documentId },
  {
    jobId: `doc:${documentId}`,        // 幂等键
