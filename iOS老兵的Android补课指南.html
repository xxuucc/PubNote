一句话结论

Android 的技术难点不在语法，而在三个 iOS 没有的维度：可编程的构建体系、设备与厂商的持续碎片化、以及一套不可逆的签名 / 版本 / 合规资产链。把这三件事按顺序补齐，iOS 经验就能直接复用六成以上。

两个颠覆性认知

iOS 经验直接套用会出事故的地方，入职第一周就要接受。

认知一 · 碎片化是产品级风险

iOS 只需适配 6~8 种屏幕；Android 要面对上百种 DPI 组合、十几代系统版本共存、三星/小米/华为等厂商深度定制 ROM。适配不是"做完就好"，是持续工程。

认知二 · 签名密钥不可再生

iOS 证书丢了重签即可；Android 上应用签名密钥丢了，除非接入了 Google Play App Signing（托管正式密钥），否则没有任何官方途径找回。这是入职第一天就该落库备份的事。

L3 · 最容易"翻译错"的三项，展开看反例

Keystore：iOS 开发者习惯"证书过期→重新生成→重新签名"，这套动作在 Android 上是灾难。签名密钥是应用在市场里的身份指纹，微信/高德等 SDK 把你的 SHA-1 指纹写进了他们的后台，密钥一换，所有平台的绑定同时失效。

targetSdk：它不是一个"最低支持版本"式的数字，而是"我愿意接受哪一档系统行为约束"的声明。调高它等于主动打开一批新限制（边到边、前台服务类型、通知权限），必须配一轮完整回归。

Build Configuration：iOS 的 Configuration 主要切编译宏和签名；Android 的 flavor 能替换整个源码目录与资源目录，编译期就能产出行为不同的 App，这是"渠道包"这件事成立的技术前提。

03

工程与构建层（A）

iOS 开发者的最大不适应：Android 的一切构建设置都是文本代码。改签名、加依赖、配渠道，都是改文件 + git 提交，没有 GUI 面板。

3.1 Gradle：Android 的"可编程 Xcode"

android/
├── settings.gradle(.kts)                      # 声明哪些模块参与构建、插件仓库
├── build.gradle(.kts) [根]                    # 全局插件版本（AGP / Kotlin 版本锁定在此）
├── gradle/wrapper/gradle-wrapper.properties   # Gradle 本体版本（分发版本）
└── app/build.gradle(.kts)                     # 模块级：applicationId、SDK 版本、签名、依赖
  • applicationId（如 com.company.app）≈ iOS Bundle ID，发布后永不可改，改了等于新 App。
  • 三个 SDK 版本号的语义：minSdk（最低支持系统版本，低于则无法安装）/ targetSdk（声明"已按此版本行为适配"，影响系统对你的行为限制）/ compileSdk（编译用 API 版本，尽量最新）。
  • 版本号规则：versionCode 整数递增（上传商店后不可降级）；versionName 是展示字符串（"2.3.1"）。
  • Flutter 项目建议写 minSdk = flutter.minSdkVersion，跟随 Flutter 引擎要求，避免手写死版本。
  • 【坑】targetSdk 不只是数字：设为 35，系统会强制启用 Android 15 的边到边显示等新行为——改 targetSdk = 一轮真回归测试，不是改配置了事。
L3 · AGP / Gradle / Kotlin 版本对齐矩阵（Flutter 项目高频事故源）

AGP（Android Gradle Plugin）、Gradle 本体、Kotlin 插件三者版本强约束（如 AGP 8.x 要求 Gradle 8.x、JDK 17）。Flutter 升级后经常报 "requires Gradle X / AGP Y"。

处理顺序：查 Flutter 官方兼容表 → 升 Gradle wrapper → 升 AGP → 升 Kotlin 插件 → ./gradlew clean。升级 Android Studio 时它可能顺手改坏这些版本，每次升级 Studio 后先跑一次构建。

3.2 依赖管理

  • 依赖仓库：Google Maven + Maven Central（对标 CocoaPods trunk）；国内项目常加阿里云镜像解决下载慢。
  • 【坑】依赖冲突：两个库共同依赖不同版本的同一个库时，Gradle 默认取最高版本，可能引发运行时 NoClassDefFoundError。用 ./gradlew app:dependencies 查看依赖树，冲突时用 resolutionStrategy 强制统一。
  • AndroidX 是现代库的统一前缀（对标 UIKit 系框架），非 AndroidX 的旧 support 库已死，见到 com.android.support:* 说明这个库不要用。
  • 【iOS 习惯纠偏】iOS 依赖锁在 Podfile.lock；Android 对应 gradle.lockfile（默认不开启）。建议开启 dependencyLocking，否则某三方库发个坏版本，你的 CI 就炸了。

3.3 构建变体：Build Types 与 Product Flavors

BuildTypes：debug / release（+ 自定义，如 staging）——对标 iOS 的 Build Configuration
Flavors：free / paid；或国内渠道 google / huawei / xiaomi / oppo…——对标多个 Target

两者笛卡尔积组合成变体（如 xiaomiRelease）。渠道差异（不同商店统计 SDK、图标、支付 SDK）全部声明在 flavor 的 dimension 里，一份代码出 N 个渠道包。

// app/build.gradle.kts 示例
android {
    buildTypes {
        release {
            isMinifyEnabled = true          // 开 R8 混淆
            isShrinkResources = true        // 收缩未用资源
            proguardFiles(getDefaultProguardFile("proguard-android-optimize.txt"),
                          "proguard-rules.pro")
        }
    }
    flavorDimensions += "channel"
    productFlavors {
        create("google") { dimension = "channel"; applicationIdSuffix = ".g" }
        create("huawei")  { dimension = "channel" }
    }
}

关键差异

iOS 不会在编译期改变代码逻辑结构；Android 的 flavor 可以替换整个源码目录（src/huawei/java/... 优先于 src/main/），可实现渠道级真差异，不只是配置差异。

04

机型与系统适配层（B）

iOS 上"适配"是一次性任务；Android 上它是一条持续的产品风险线。

4.1 屏幕适配

单位体系（对照 iOS 的 pt）：

  • dp：密度无关像素，≈ iOS 的 pt。物理像素 = dp × 屏幕密度。
  • sp：随用户系统字体缩放倍数缩放的 dp——所有文字用 sp，行高 / 间距用 dp。用户把字体调到 1.3 倍时，写死 dp 的文字行会截断，这是 iOS 开发者最常见的适配 bug。
  • 密度桶：mdpi(1x) / hdpi(1.5x) / xhdpi(2x) / xxhdpi(3x) / xxxhdpi(4x)。图标类资源按桶出图，或统一用 Vector Drawable（XML 矢量，对标 PDF 矢量资产，强烈推荐，一份文件全密度通吃）。

布局响应性要求比 iOS 高：

  • 分屏（Android 7+）、自由窗口、折叠屏展开（大屏手机秒变平板）——Activity 可能随时改变尺寸，必须保证布局自适应，不能假设"竖屏全屏"。
  • android:resizeableActivity="true" 是默认预期；Flutter 应用整体自适应较好，但要处理键盘弹出（Android 键盘默认遮挡输入框，Flutter 中需设 resizeToAvoidBottomInset 并实测各厂商键盘行为——国产 ROM 键盘高度上报经常不准，这是知名坑）。
  • 刘海屏：Android 用 WindowInsets 体系获取安全区（对标 env(safe-area-inset-*)）。Flutter 的 SafeArea 默认可用，但 Android 15 边到边强制后需实测沉浸状态栏是否被内容穿透。

4.2 系统版本碎片化与 targetSdk 政策（硬性合规线）

API 版本演进与商店强制要求时间线
API 版本商店强制要求（更新时间线）对开发者的关键影响
API 26（历史）通知必须走 NotificationChannel，否则通知静默丢失
API 29Scoped Storage 生效不能随意读写公共存储，改用 MediaStore / SAF
API 31—四大组件必须显式声明 android:exported，含 intent-filter 的组件不写直接装不上
API 33—通知权限改为运行时申请（POST_NOTIFICATIONS）；引入 Photo Picker
API 342024-08-31 起更新需 target ≥ 34前台服务必须声明具体类型（camera / location / mediaPlayback 等），滥用被拒
API 352025-08-31 起新应用与更新需 target ≥ 35边到边强制启用；16KB 内存页要求（见下）

16KB 内存页对齐（2025 新硬线，Flutter 项目必查）

自 2025-11-01 起，target Android 15+ 且含原生 so 库的应用必须按 16KB 页对齐，否则 Play 拒收（2026-05-01 起完全封锁更新）。Flutter 引擎及含 native code 的插件（ffmpeg / sqlite / 加密库等）需升级到已对齐版本。

验证方式：NDK 28+ 构建，或用 llvm-readelf -l 检查 so 的 LOAD 段对齐值 ≥ 16384。Flutter 主线引擎已适配，风险在旧插件，集成前查插件 changelog。

【工作流建议】每年 8 月底是 Play 的 targetSdk 死线（"最新系统版本发布 1 年内必须 target"），把"annual targetSdk 升级 + 回归测试"写进团队日历。

4.3 厂商碎片化（OEM ROM）——iOS 完全没有的维度

同一份 APK 在小米、华为、三星上表现可能不同，因为厂商深度定制了系统行为。

厂商问题域典型现象应对
自启动管理用户不手动允许"自启动"，推送进程被杀、收不到通知引导用户到设置页开启；UI 上做"保活指引"页面
省电杀后台MIUI / EMUI 激进的电池优化直接杀后台服务申请电池优化白名单（REQUEST_IGNORE_BATTERY_OPTIMIZATIONS，商店审核会追问用途）；接受"保不住"的现实，靠厂商推送通道兜底
推送通道国内无 GMS → 没有 FCM华为 Push Kit、小米 Push、OPPO / vivo Push、厂商聚合 SDK（个推 / 极光）。iOS 一套 APNs 通吃的体验在国内 Android 不存在
键盘与手势各家键盘高度上报、全面屏手势区域不同真机测试；键盘相关交互留余量
权限入口差异自动跳转权限设置页在部分 ROM 失效跳转失败降级为"请到设置 > 应用管理"文案引导

测试策略结论

真机矩阵至少覆盖：小米（MIUI / 澎湃 OS）、华为（HarmonyOS，注意新华为设备已是鸿蒙 NEXT，不再兼容 APK，需单独评估是否出鸿蒙版）、OPPO / vivo、三星（国际标准行为参照）、一台原生 Android（Pixel，验证无厂商干扰时的标准行为）。

模拟器只能覆盖行为基线，省电 / 推送 / 键盘问题只有真机能暴露。

4.4 系统行为差异速查

  • 返回键 / 手势：iOS 没有系统返回概念。Android 有返回手势 / 按键，Flutter 用 WillPopScope / PopScope 处理拦截（Android 14+ 预测性返回手势还要求提前声明）。左滑返回 App 内导航 ≠ 系统返回，两套都要处理。
  • 深色模式：Android 系统级切换，values-night/ 资源目录自动切换。Flutter 的 MediaQuery.platformBrightness 可用，但原生页面、启动画面、通知图标要单独适配。
  • RTL：阿拉伯语等从右向左布局。iOS 你可能没做过 RTL；Android 布局属性要用 start/end 而非 left/right（Flutter 的 EdgeInsetsDirectional 等）。接国际项目前确认需求。
  • 图标：Adaptive Icon（前景层 + 背景层 XML），不同启动器可能裁成圆 / 方 / 圆角方。给一层 PNG 会被各家启动器压变形。启动画面用 SplashScreen API，无法自定义展示时长。
05

运行时与系统集成层（C）

不要用 AppDelegate 的心智理解 Android：它没有单一入口，任何一个组件都可能被系统或别的 App 单独拉起。

5.1 权限模型：一个权限的"三段式"认知

Android 权限 = Manifest 声明 + 运行时请求 + 用户可能永久拒绝，且行为随 API 版本漂移。

  • 安装时权限（normal 级）：INTERNET、VIBRATE 等，声明即得（对标 iOS 无感权限）。
  • 运行时权限（dangerous 级，API 23+）：相机、定位、麦克风、存储等。必须在交互时机请求（Flutter 用 permission_handler 统一封装）。
  • "不再询问"状态：用户两次拒绝后系统不再弹窗——必须检测 shouldShowRequestPermissionRationale 引导去设置页（iOS 只有一次 denied 后只能引导设置，Android 这里的状态机更复杂）。
  • 特殊权限：SYSTEM_ALERT_WINDOW（悬浮窗）、电池优化白名单等，要去系统设置页手动开，运行时 API 只能发起跳转。
L3 · 近年的"降级替换"趋势（Android 正在向 iOS 隐私模型收敛）
  • 精确 / 模糊定位二选一（API 31+，对标 iOS 精确位置开关）；
  • 仅本次允许（对标 iOS "Allow Once"）；
  • 照片部分授权（API 34，对标 iOS Limited Photos）；
  • Photo Picker（API 33+）：无需任何权限即可选图，优先用它替代读存储权限。

5.2 组件模型：四大组件

组件职责与 iOS 的差异
Activity可交互界面（≈ UIViewController）多个 Activity 以栈（Task / Back Stack）管理，别的 App 可以直接跳到你的某一个 Activity
Service / 前台服务后台任务载体API 34 起必须声明类型且用途不符会被拒审；常驻服务必须挂常驻通知
BroadcastReceiver系统事件监听对标 iOS 通知但跨 App；Android 13 起大部分系统广播需动态注册
ContentProvider跨 App 数据共享相册、通讯录通过它读取，iOS 侧无对等物

Flutter 应用通常只有一个 Activity（FlutterActivity），多数 iOS 转型者感知不到；但接 SDK（支付、登录）时 SDK 会插自己的 Activity，返回栈行为就变复杂了。

常驻后台服务（音乐、导航、运动）必须挂常驻通知——用户会看到你的"永远杀不掉的通知"，这是产品体验设计的一部分，不是纯技术细节。

5.3 进程与后台：比 iOS 更激进的"被杀"世界

  • LMK：内存不足按优先级杀进程（对标 Jetsam，但阈值与策略更激进且厂商可改）。
  • Doze 模式：设备静止 / 息屏后进入深度休眠，定时器、网络被系统批量延迟（iOS 无此级别限制）。AlarmManager 的精确闹钟需要 SCHEDULE_EXACT_ALARM 权限（API 31+ 需用户授权）。
  • 给 Flutter 开发者的实操结论：任何"离开 App 后台继续做事"的需求（上传、下载、倒计时通知），都要走前台服务 + 常驻通知的路线，纯 Dart 层的 Timer 在后台会被冻结。社区方案：flutter_background_service、workmanager（对标 iOS 的 BGTaskScheduler，但 Android 端调度更不确定——WorkManager 只保证"最终执行"，不保证准时）。

5.4 深链

  • Deep Link（自定义 scheme，myapp://page）：无验证，任何 App 都能声明同 scheme → 有劫持风险，仅作兜底。
  • App Links（https 链接）：域名下托管 /.well-known/assetlinks.json（内容含应用签名的 SHA-256 指纹）→ 系统验证通过后 https 链接直接进 App 不弹选择框。与 iOS 的 AASA + Universal Links 机制完全同构，理解成本为零。区别：验证更宽松，但失败时静默降级为"弹应用选择框"，排查时要主动看 adb shell pm verify-app-links 结果。
  • Flutter 中处理：go_router 等路由库声明 scheme / host，在 Activity 的 onNewIntent 时把 intent 传给 Flutter（Flutter 默认已处理热重启后的 deep link，但冷启动时的 initial link 要确认路由库版本支持）。

Flutter Android 侧集成层（D）

iOS 转 Flutter 最容易漏改的不是 Dart 代码，而是 android/app/src/main/AndroidManifest.xml。

6.1 AndroidManifest：Flutter 项目的"信息中枢"

  • 权限声明（<uses-permission>）、显示名（android:label）、主题、android:exported；
  • 深链 intent-filter 挂在 FlutterActivity 上；
  • 【坑】release 包关掉调试网络配置残留；
  • 【坑】android:allowBackup="true" 默认开启——本地明文存储的用户 token 会被系统备份到云端，敏感数据要么加密，要么在 backup rules 里排除。

6.2 Platform Channel 实战要点

通道类型语义典型场景
MethodChannel请求-响应（一次调用一次返回）调用原生 SDK 单个方法
EventChannel原生 → Dart 持续数据流传感器、电量变化、推送到达
BasicMessageChannel双向自由消息高频双向通信

易错细节

  • 通道名两端必须完全一致（字符串硬编码容易拼错，建议放常量文件）；
  • 数据仅支持可编解码类型（null / bool / num / String / List / Map / Uint8List），自定义对象要自己写 Codec——iOS 侧转 JSON 字典是最省事的方案；
  • 主线程约定：Android 侧 MethodChannel 默认在主线程回调，耗时要切协程 / 线程再 invokeMethod 回主线程；
  • 生命周期错配：页面销毁后 Dart 侧还有 invokeMethod → 原生侧判空防崩；原生侧在 Activity 重建（旋转 / 进程恢复）后用旧 channel 回调 → Dart 已收不到，EventChannel 要在 onListen / onCancel 中正确注册注销。
// Android 侧：耗时任务不要阻塞主线程
class PayChannel(private val activity: Activity) : MethodChannel.MethodCallHandler {
    override fun onMethodCall(call: MethodCall, result: MethodChannel.Result) {
        if (call.method != "pay") return result.notImplemented()
        CoroutineScope(Dispatchers.IO).launch {
            val ok = runCatching { doPay(call.argument("orderId")!!) }.getOrDefault(false)
            activity.runOnUiThread { result.success(ok) }   // 回调切回主线程
        }
    }
}

6.3 插件与原生依赖治理

  • pubspec.yaml 引插件后，Android 侧的真实依赖树在 android/build.gradle 生成的产物里——插件本身还会带 Gradle 依赖（对标：一个 CocoaPods 里嵌套了 SPM 依赖）。冲突时在 app/build.gradle 用 configurations.all { resolutionStrategy } 强制版本。
  • 插件质量三查：①是否仍在维护（Flutter 版本升级后旧插件是最常见的编译障碍）；②是否有原生依赖（涉及 16KB 对齐、so 冲突）；③是否要求升 minSdk（有的插件强制 minSdk 24+，会把整包最低版本抬上去——这是选型时就该看的）。
  • 需要写自定义插件时：Flutter 命令生成 Plugin 模板，Kotlin 写 Android 侧，FFI（dart:ffi）适合纯计算型原生调用（对标 C 互操作）。

打包与签名层（E）

先弄清签名，再谈打包。一套密钥，两个角色。

7.1 签名体系

上传密钥

你本地持有的 .jks 文件 + 密码，用于给上传到 Play 的包签名。丢了可以重置。

App 签名密钥

接入 Play App Signing 后由 Google 托管的"正式身份"，Google 用它重签后分发给用户。丢了这个身份就没了。

【与 iOS 的核心差异】iOS 签名证书丢了重签即可（Apple 会校验你账号身份）；Android 一旦丢失正式签名密钥，没有任何找回渠道，应用等于报废（用户无法升级，只能以新 applicationId 重新发布）。

签名密钥管理制度（入职 / 立项第一天做）

  1. keystore 文件 + 密码 + alias 入密码管理器 / 公司保险库，绝不进 git；
  2. CI 打包用环境变量 / 密钥管理服务注入（key.properties 只进 .gitignore）；
  3. 接入 Play App Signing，让 Google 托管正式密钥（上传密钥丢了可重置）；
  4. 记录 keystore 的 SHA-256 指纹——它同时用于 App Links 验证、第三方 SDK 平台（微信 / 高德等）注册。
// 标准签名配置写法（密码不进 git）
val keystoreProps = Properties().apply {
    val f = rootProject.file("key.properties")
    if (f.exists()) load(f.inputStream())
}
signingConfigs {
    create("release") {
        storeFile = keystoreProps["storeFile"]?.let { file(it) }
        storePassword = keystoreProps["storePassword"] as String?
        keyAlias = keystoreProps["keyAlias"] as String?
        keyPassword = keystoreProps["keyPassword"] as String?
    }
}

7.2 AAB vs APK、ABI、16KB

  • AAB（Android App Bundle）：Play 商店强制要求（2021-08 起新应用），上传的是"中间格式"，Google 按设备动态生成按需分发的 APK（Split APKs）——用户只下载自己设备需要的资源和 ABI，包体积普遍降 30%+。flutter build appbundle 产出。注意 AAB 不能直接安装到手机测试，本地测试用 bundletool 转真 APK 或直接打 APK。
  • 国内商店不收 AAB，只收通用 APK——国内项目构建链是双轨：Play 走 AAB，国内各商店走 flutter build apk --split-per-abi 或 fat APK。
  • ABI：armeabi-v7a（32 位老设备）/ arm64-v8a（主流 64 位）/ x86_64（模拟器）。Play 要求 64 位（arm64）必含；--split-per-abi 拆分后单包体积减半以上。
  • 16KB 对齐（见 4.2）：含原生 so 的应用 target 35 时的 Play 硬门槛，上传前自查。

7.3 构建优化（release 包质量三件事）

  1. R8 混淆与收缩：isMinifyEnabled = true + isShrinkResources = true。Flutter 引擎与 Kotlin / Flutter 插件自带 consumer rules，但反射调用的原生 SDK（支付、推送、序列化库）需要手动 keep 规则，否则 release 包运行时闪退而 debug 正常——"debug 好好的，release 一启动就崩"，九成是混淆规则没写。
  2. 符号上传：混淆后崩溃堆栈是乱码（a.b.c），要把 R8 生成的 mapping.txt 归档并上传 Crashlytics / Sentry 才能还原堆栈。iOS 的 dSYM 上传心智完全平移。每个 versionCode 的 mapping 都要留档，丢失 = 该版本崩溃无法解读。
  3. 启动性能：Flutter 冷启动白屏常见于低端机与国产 ROM，手段：启动画面适配（默认系统 splash）+ Dart 主隔离预初始化 + 关注 Android Vitals 的 TTFD 指标。
# 出包三条命令（Play / 国内 / 自测）
./gradlew :app:bundleRelease                 # AAB → Play
flutter build apk --split-per-abi --release  # 分 ABI APK → 国内商店
flutter build apk --release                  # fat APK → 自测 / 分发
./gradlew app:dependencies > deps.txt        # 依赖树快照，随版本归档

7.4 国内多渠道打包

  • 渠道维度用 flavor 或 walle（美团方案，基于 V2 签名写入渠道信息，秒级出包）实现；
  • 每个渠道的统计 SDK 初始化开关 + 各商店的隐私声明差异，在 flavor 源目录隔离；
  • 【坑】多渠道 × 多 buildType 的变体数量爆炸（4 渠道 × 2 = 8 个变体），CI 要显式指定要构建的变体，别全量跑。
08

发布层（F）

发布是 Android 上唯一"iOS 经验几乎零平移"的一块：多商店、多资质、多审核标准。

8.1 Google Play 发布全流程

内部测试（Internal，≤100 人，秒级分发）
  → 封闭测试（Closed，邮件列表 / Google Group）
  → 开放测试（Open，可从商店页加入）
  → 正式版（Production，支持分阶段放量）

硬性合规清单（2025 口径）

  • targetSdk ≥ 35（2025-08-31 起新应用与更新的要求；每年 8 月底滚动上调）；
  • 含原生 so 的应用支持 16KB 页对齐（2025-11-01 起 target 35 强制）；
  • AAB 格式上传；
  • 接入 Play App Signing；
  • 新个人开发者账号：首个应用需先建封闭测试轨道，12 名测试员连续选择参与 14 天后才能申请正式发布（2024-12 起从 20 人降为 12 人；组织账号与老账号豁免；每个新 App 都要重新走一遍）——直接影响发布排期，提前 3 周规划；
  • 数据安全表单（Data Safety）：声明收集哪些数据、是否共享——与代码实际行为必须一致，撒谎会被下架；
  • 隐私政策 URL（必须可公网访问）；
  • 内容分级问卷、目标受众（含儿童则触发更严政策）、广告声明；
  • 商店素材：图标 512×512、功能图 1024×500、各机型截图。

审核与放量：Play 初审通常数小时~2 天，但事后机器 + 人工扫描持续进行；正式发布用分阶段放量（如先 10% → 50% → 100%），崩溃率异常可暂停放量——这是比 iOS 更细粒度的发布控制，建议默认开启。

上架后立即做的：Play Console 的 Pre-launch Report（自动真机测试）与 Android Vitals 基线确认。

8.2 国内应用商店发布

前置资质（比技术更容易卡住流程的部分）

  1. 软件著作权（软著）：多数商店上架必备，申请周期数周，提前办；
  2. ICP 备案 / App 备案：2023 年起工信部要求 App 备案（主体备案 + App 备案），无备案号商店直接拒收——国内发布的硬门槛，走企业主体 + 服务器在国内；
  3. 《隐私政策》符合《个人信息保护法》《网络安全法》：权限用途逐条说明、SDK 清单披露（第三方 SDK 收集信息也要列）；
  4. 特定行业需额外资质：金融类牌照、医疗类审批、教育类备案等；
  5. 各家商店（华为 / 小米 / OPPO / vivo / 应用宝…）各自注册开发者账号（企业账号需营业执照 + 对公验证），每个商店的审核标准、素材尺寸、更新说明规范都不同，首次全流程预留 2~4 周。

技术差异清单：无 GMS → 推送用厂商通道 / 聚合 SDK；支付接微信 / 支付宝（非 IAP 垄断，虚拟商品也可以走第三方支付——与 iOS 30% 抽成规则完全不同）；地图 / 定位换高德 / 百度（对标换掉 MapKit）；商店审核对权限滥用、强制索权、启动弹窗极敏感——"启动即弹权限"在国内商店是高频驳回项，权限请求要跟功能场景绑定。

多渠道发布节奏：建议主版本统一日发布，但各商店审核时长不一（1~7 天），用 CI 出渠道包 + 各商店后台分别提审，建立渠道发布状态表跟踪。

8.3 版本与灰度策略

  • 版本号策略：versionCode 建议用规则化数字（如 MMmmpp 或构建流水号），保证单调且可追溯；
  • 灰度：Play 用分阶段放量；国内商店多数支持"按比例发布"（华为 / 小米有类似能力），部分商店只能全量——以最慢的商店为准规划回滚预案；
  • 回滚：Android 不能撤回已装版本，只能发布更高 versionCode 的修复版——所以"发版前真机冒烟 + 灰度观察 24h Vitals"是纪律不是建议。

质量与运维层（G）

Android 的线上质量多了一个 iOS 没有的独立类别：ANR。而它还会反过来惩罚你的商店排名。

9.1 监控三件套

维度工具与 iOS 的差异
崩溃Crashlytics / Sentry多了 ANR 类别（主线程 5s 无响应，用户可弹"关闭应用"）——ANR 往往是 Flutter 侧主隔离阻塞或原生主线程 IO 引起
性能基线Android Vitals（Play Console 内置，免费）直接影响商店搜索排名（崩溃率 / ANR 率过高会被降权甚至警示）——Play 特有的运营级惩罚
自定义性能Firebase Performance / 自建关注冷启动（TTFD）、页面帧率

ANR 排查必备技能：会读 /data/anr/ traces（或通过 Play Console 下载聚合的 ANR 堆栈）——主线程在等锁 / 等 binder / 做 IO 是三大常见原因。

9.2 兼容性测试矩阵（最低配置建议）

  • 真机 5 台：Pixel（标准行为）+ 三星（国际市占第一）+ 小米 + 华为 / 荣耀 + OPPO / vivo（任选）；
  • 系统版本：最低支持版本 1 台 + 最新正式版 1 台；
  • 状态矩阵：深色模式开 / 关、字体缩放 1.0 / 1.3、分屏、弱网（飞行模式切换）、权限全拒 / 全给、进程被杀后恢复（开发者选项里"不保留活动"打开后回归一遍，模拟激进后台）；
  • Play Console 的设备目录可查真实机型分布，按用户分布配测试机，不按情怀配。

9.3 Flutter 特有的质量项

  • Dart 主隔离阻塞同样会引发 ANR（用户手势事件在平台线程分发到 Dart 后被阻塞）——耗时计算用 compute() / Isolate.run；
  • 插件升级后必须回归原生侧行为（权限申请文案、通知、deeplink），因为插件可能内含原生代码变更；
  • 崩溃日志两套体系并存：Dart 异常（Flutter Error）与原生崩溃（tombstone / NDK crash），Crashlytics 两边都要配（FlutterError.onError + PlatformDispatcher.onError）。
// 崩溃双通道接入
FlutterError.onError = (details) {
  FirebaseCrashlytics.instance.recordFlutterFatalError(details);
};
PlatformDispatcher.instance.onError = (error, stack) {
  FirebaseCrashlytics.instance.recordError(error, stack, fatal: true);
  return true;   // 阻止默认的进程终止
};

安全层（H）

Android 的安全基线比 iOS 松，但暴露面更大：组件可被任意 App 调用，安装包可被任意反编译。

明文传输

Android 9+ 默认禁 cleartext HTTP；要用 HTTP 必须在 networkSecurityConfig 显式放行——这是 iOS ATS 的同构物，理解成本为零。

组件暴露

exported="true" 的 Activity / Service 可被任意第三方 App 调起。敏感页面加签名校验或设 exported="false"。

数据存储

敏感数据用 EncryptedSharedPreferences / flutter_secure_storage（底层 Keystore）；allowBackup 排除敏感文件；调试残留（debuggable、日志、测试后门）在 release 中关闭。

加固与反逆向

国内发布惯例接入加固（腾讯乐固 / 360 / 爱加密等），防 dex 反编译与二次打包；Play 侧用 R8 + Play Integrity API（对标 DeviceCheck / App Attest）。

密钥安全（把前文串起来的一条线）

任何硬编码在客户端的 secret 都视为公开（与 iOS 同理）。高德 / 微信等平台的 App 签名绑定（用你的 keystore 指纹绑定 SDK）是 Android 侧防冒用的主要手段——这就是为什么 keystore 指纹变更要走全平台更新流程，也反过来要求 keystore 终身不变。

<!-- AndroidManifest：只放行确实需要明文的那一个域名 -->
<application android:networkSecurityConfig="@xml/network_security_config" ... >
<!-- res/xml/network_security_config.xml -->
<network-security-config>
    <base-config cleartextTrafficPermitted="false" />
    <domain-config cleartextTrafficPermitted="true">
        <domain includeSubdomains="false">legacy.internal.example</domain>
    </domain-config>
</network-security-config>

术语表与自测

先扫术语消除歧义，再用 5 道题验一下哪一章还没读透。

术语表

AGP（Android Gradle Plugin）
Gradle 上构建 Android 的插件，与 Gradle 本体、Kotlin 插件强版本约束。
applicationId
应用在市场里的唯一身份，≈ Bundle ID，发布后不可更改。
targetSdk
声明"已按该版本系统行为适配"，决定系统对你施加哪些限制，不是最低支持版本。
Build Type / Flavor
前者切 debug/release 编译配置，后者切渠道与业务变体，二者笛卡尔积形成 variant。
dp / sp
密度无关像素 / 随字体缩放的可伸缩单位；间距用 dp，文字用 sp。
LMK / Doze
低内存杀进程机制 / 深度休眠模式，二者共同造成 Android 后台被激进回收。
ANR
Application Not Responding，主线程 5s 无响应，iOS 没有的独立崩溃类别。
AAB
Android App Bundle，Play 强制上传格式，按设备动态下发 Split APK。
Play App Signing
Google 托管正式签名密钥的服务，使上传密钥可重置。
16KB 页对齐
native so 的 LOAD 段需按 16384 字节对齐，2025 起 Play 的硬门槛。
assetlinks.json
App Links 的域名验证文件，内含应用签名 SHA-256 指纹。
mapping.txt
R8 混淆映射表，用于还原崩溃堆栈，必须按 versionCode 归档。

自测 · 5 题

  1. 把 targetSdk 从 34 改到 35，为什么不能当作"改个数字"？
    看答案

    它声明你接受 Android 15 的行为约束：边到边显示强制启用、前台服务类型、16KB 对齐等同时生效。这会改变运行期行为，必须配一轮完整回归，按版本发布的流程走。

  2. 用户把系统字体调到 1.3 倍，你的页面文字被截断。最可能的原因？
    看答案

    文字容器的高度用 dp 写死。文字用 sp 会随 fontScale 放大，而 dp 高度不变，于是裁切。文字区域应改为可伸缩约束（wrap_content / minHeight），不要用固定 dp 行高。

  3. debug 包一切正常，release 包启动即崩。优先查什么？
    看答案

    R8 混淆规则。反射调用的支付 / 推送 / 序列化 SDK 需要 keep 规则，否则类名被改后反射找不到类，抛 ClassNotFound / NoSuchMethod。同时确认 mapping.txt 已归档，否则堆栈无法解读。

  4. 推送在 Pixel 上正常，在小米 / 华为上收不到。为什么？
    看答案

    国内无 GMS，FCM 不可用；且 MIUI / EMUI 的自启动管理与省电策略会杀后台进程。需要接厂商推送通道（或聚合 SDK），并引导用户开启自启动与电池优化白名单。

  5. 为什么 Android 发布后"回滚"这个词不成立？
    看答案

    已安装到用户设备上的版本无法撤回，市场也不允许降低 versionCode。唯一路径是发布更高 versionCode 的修复版，因此灰度观察与真机冒烟是发布流程的组成部分。
