放射线 · 基础支撑

从核心 LLM 指向八个系统，表示「这一层为模型能力提供底层支撑」。架构与训练是地基，对齐与推理是上层，越靠近核心越不可绕过。

弧线 · 协同演进

相邻系统之间的弧线表示「二者在设计上互相牵制」。架构决定推理的显存上限，推理的需求又反过来推动架构（如 GQA、MLA）的演进。

虚线 · 信息流动

表示数据或信号的方向。请求从用户进入，穿过检索、推理、工具、输出，最终回流到观测与评测——这是一条闭环，不是单向流水线。

贯穿线 · 评测与安全

评测与安全不占据某一段链路，而是横跨全部七个系统。它既是裁判，也是免疫系统：任何一层改动，都要在这里留下可比较的证据。

03 · Model Internals · 微观视角

模型内部：向量 × 层数 × 专家 × 调度员 × 输出

用「一群专家顾问团队，一层层开会审材料」这个统一比喻，把整个推理过程串成一条可播放的动画。 本次演示的案例问题是：「写一段 FastAPI 的接口代码」 —— 文字先被分词、翻译成向量（数字简历），再由每层楼里的 调度员（Router / Gate）打分，只叫醒最对口的 2 个领域专家来修改这份向量，改完交给上一层；最后 向量被解码成 Token，通过 SSE 流式传输到用户眼前。

04 · Application Layer · 落地视角

应用层知识体系

模型能力只是起点。真正产生价值的是把能力组织成产品与流程 —— 下面分别给出个人开发者与企业两条落地路径。

L1

基础底座 · 决定你能不能“看懂”模型

这一层不追求深，但必须扎实。它决定了后面学习是“照抄教程”还是“真正理解”。

Python 工程能力 线性代数 · 概率统计 机器学习基础 PyTorch Linux / Git 数据处理 pandas
L2

模型能力 · 理解大模型本身

从“会调 API”进阶到“知道模型为什么这样回答”，是能力分水岭。

Transformer 原理 注意力机制 层数 / 专家数 / MoE / Router Prompt 工程 SFT / LoRA 微调 模型评测与对比 量化与本地部署
L3

应用工程 · 把模型变成可用系统

绝大多数开发者真正的战场。模型是黑盒，但工程链路是你能完全掌控的部分。

RAG 系统设计 向量数据库 文档切分与重排 Agent 编排 Function Calling / MCP SSE / WebSocket 流式 上下文工程 可观测与追踪 缓存与成本控制
L4

产品落地 · 让能力真正被使用

技术之外的维度。能否判断“什么场景值得做”，往往比“能不能做出来”更重要。

需求拆解与场景选择 人机协作交互设计 评测集与回归测试 数据飞轮 安全与合规 延迟 / 成本权衡

1先买模型，再找场景
典型反模式。正确顺序是：先盘点高频、高价值、可衡量的业务痛点，再倒推需要什么模型能力。否则很容易做出“演示很惊艳、上线没人用”的系统。
2把 RAG 当成“接个知识库就完事”
检索质量才是 RAG 的上限。文档切分策略、embedding 选型、重排序、查询改写、上下文组装，每一环都会显著影响最终效果。检索不准，模型再强也会一本正经地胡说。
3没有评测集，靠“感觉”迭代
没有评测集就无法判断一次改动是变好还是变差。建议从第一天就积累真实场景的问答对，建立自动 + 人工结合的回归评测流程。
4只关注效果，不关注成本与延迟
在 Demo 阶段效果优先没问题，但进入生产后，单位任务成本、P95 延迟、并发能力往往才是项目能否持续的关键。模型分级 + 缓存 + 上下文压缩是常用手段。
5忽视人的角色，追求完全自动化
多数高价值场景的最佳形态是“人机协作”：AI 完成 80% 的初稿或检索，人做最终判断。合理设计审核与反馈节点，反而能显著提升整体效率与信任度。
