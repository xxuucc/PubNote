第 1 章 提示词工程全景

1.1 什么是提示词工程

提示词工程（Prompt Engineering, PE）是通过设计、优化和管理输入文本（Prompt），引导大语言模型产出高质量、可控、可复现结果的工程学科。它不是"写咒语"，而是包含需求拆解、结构设计、迭代调试、量化评测、版本管理的完整方法论。

输出质量 = f(模型能力, 提示词质量, 上下文质量, 推理参数)
1.2 程序员的天然优势
程序员已有能力在提示词工程中的映射
结构化思维 / 抽象能力提示词模块化、模板化设计
Debug 经验提示词故障定位与迭代优化
API 调用经验模型 API 集成、流式处理、错误重试
测试思维评测集设计、回归测试
版本控制（Git）提示词版本管理、A/B 测试
系统设计能力Agent 编排、RAG 架构、多模型路由
1.3 提示词工程 vs 微调 vs RAG
维度提示词工程微调RAG
成本极低（仅 API）高（算力+标注）中（向量库+检索）
知识更新实时慢（重训练）实时
适合场景风格控制、任务拆解领域术语、特定语气事实问答、私有知识
迭代速度分钟级天~周级小时级
决策原则先用提示词工程做到 80 分，再考虑 RAG 补事实，最后才用微调补风格和术语。三者经常组合使用。
1.4 发展历程
  • 2020：GPT-3 发布，Few-shot 成为研究热点
  • 2022：Chain-of-Thought 论文发表，推理能力跃升
  • 2023：GPT-4 发布，Agent、RAG、工具调用爆发
  • 2024：多模态、MCP、结构化输出成标配；向"上下文工程"演进
  • 2025+：Agentic AI 成主流，核心从单轮提示转向多轮编排+工具调用+状态管理

第 2 章 大模型底层原理（程序员视角）

2.1 Token 机制

Token 是 LLM 处理文本的基本单位。英文 1 token ≈ 4 字符，中文 1 token ≈ 1~2 汉字，代码 1 token ≈ 3~4 字符。

必须知道上下文窗口 = 输入 + 输出；计费按 token；优化技巧：用缩写、合并重复、移除无意义空白。
import tiktoken
enc = tiktoken.encoding_for_model("gpt-4o")
tokens = enc.encode("你好，世界！Hello, World!")
print(len(tokens))
2.2 注意力机制对提示词的启示
  • 位置敏感：开头和结尾注意力更强（"Lost in the Middle"），关键指令放首尾
  • 相关聚集：相关信息放一起比分散效果好
  • 长上下文衰减：超过一定长度后中间内容召回率显著下降
2.3 采样参数详解
参数作用推荐值
temperature随机性，0=确定代码/事实: 0~0.3；创意: 0.7~1.0
top_p核采样0.9~1.0，与 temperature 二选一调
max_tokens输出最大长度根据任务设，避免截断
frequency_penalty惩罚重复 token去重设 0.5~1.0
presence_penalty惩罚已出现 token创意设 0.3~0.6
stop停止序列结构化输出截断

第 4 章 提示词基础语法与结构

4.1 标准结构八模块
┌─────────────────────────────────┐ │ 1. 角色设定（Role） │ 你是谁 ├─────────────────────────────────┤ │ 2. 任务描述（Task） │ 做什么 ├─────────────────────────────────┤ │ 3. 背景信息（Context） │ 相关背景 ├─────────────────────────────────┤ │ 4. 输入数据（Input） │ 待处理内容 ├─────────────────────────────────┤ │ 5. 示例（Examples / Few-shot） │ 参考样例 ├─────────────────────────────────┤ │ 6. 约束条件（Constraints） │ 不能做什么 ├─────────────────────────────────┤ │ 7. 输出格式（Output Format） │ 怎么输出 ├─────────────────────────────────┤ │ 8. 质量标准（Quality Criteria） │ 好坏标准 └─────────────────────────────────┘
4.2 角色设定模板
你是一位拥有 10 年经验的 [领域] 专家，擅长 [具体技能]。
你的沟通风格是 [风格描述]。
请以该身份回答以下问题。

程序员常用角色：高级全栈工程师、资深 iOS 开发者、前端架构师、安全工程师、DevOps 工程师、技术文档工程师。

避免"你是一个有用的助手"这种空泛描述，角色要具体。
4.3 指令清晰度：反例 vs 正例
❌ 反例：帮我写个函数
✅ 正例：用 Python 写一个函数，输入是一个整数列表，
   返回列表中所有偶数的和。函数名为 sum_even，
   需要处理空列表的情况（返回 0），并添加类型注解和 docstring。
4.4 分隔符与结构化标记

常用分隔符：---、```、【输入】、<input> XML 标签（模型理解最好）、###。

最佳实践对用户输入内容始终用分隔符包裹，防止 Prompt Injection。
4.5 输出格式控制
请以 JSON 格式输出，严格遵循以下 schema：
{
  "summary": "string，不超过100字",
  "keywords": ["string"],
  "sentiment": "positive|negative|neutral",
  "confidence": 0.0-1.0
}
只输出 JSON，不要输出任何其他文字。

进阶：使用结构化输出 API（Response Format / Tool Use）比纯文本约束更可靠。

第 5 章 经典范式全集

5.1 Zero-shot / Few-shot

Zero-shot：直接给指令，适合简单明确任务。

Few-shot：提供 2~5 个示例，覆盖不同类别，格式与实际输入完全一致。注意近因效应（最后一个示例影响大）。

5.2 Chain-of-Thought（思维链）
问题：一个商店有 23 个苹果，卖出 17 个，又进货 15 个，现在有多少个？
请一步步思考，然后给出答案。

Zero-shot CoT 只需加一句"请一步步思考（Let's think step by step）"。适用：数学推理、逻辑题、多步决策、代码 Debug。

5.3 Self-Consistency（自洽性）

多次采样（temperature > 0）取多数答案，数学推理可提升 10~20%，但成本乘以 N。

5.4 Tree of Thoughts（思维树）
针对以下问题，请：
1. 生成 3 种不同的解题思路
2. 对每种思路评估（可行性 1-10）
3. 选择最高分思路，给出完整解答
5.5 ReAct（推理+行动）
Thought: 我需要先了解...
Action: search("关键词")
Observation: [工具返回结果]
Thought: 基于搜索结果...
Final Answer: ...

这是 Agent 的基础范式，交替推理和行动。

5.6 Reflexion（反思）

初版答案 → 自我批评（列 3 个问题）→ 改进后最终答案。

5.7 范式选择决策树
任务简单、格式明确？ ├─ 是 → Zero-shot 或 Few-shot └─ 否 → 需要推理？ ├─ 是 → 需要多步/工具？ │ ├─ 是 → ReAct / Agent │ └─ 否 → CoT └─ 否 → 需要高准确率？ ├─ 是 → Self-Consistency / ToT └─ 否 → Zero-shot CoT

第 6 章 高级提示词技术

6.1 元提示词（Meta-Prompting）

让模型自己优化提示词：给出原始提示词 + 问题描述，要求分析不足并给出优化版。

6.2 提示词链（Prompt Chaining）

复杂任务拆为多步，每步输出作为下一步输入。如代码审查：理解 → 分析问题 → 修复建议。优势：每步聚焦、错误可定位、可人工介入。

6.3 路由提示词

先用分类提示词判断任务类型（code_generation / review / explanation / debugging），再路由到专门提示词。

6.4 知识生成提示词

先让模型生成 5 个关键事实，再基于知识回答问题。

6.5 否定约束的正确用法
❌ 不要写得太长        → ✅ 输出不超过 200 字
❌ 不要有错误          → ✅ 所有代码必须可编译运行，包含 import

不要只说"不要做 X"，要说明"应该做 Y"。

6.6 温度与提示词配合
  • 高 temperature（0.8+）：创意写作、头脑风暴，提示词应宽松
  • 低 temperature（0~0.3）：代码、数据提取，提示词应精确
  • 动态调整：先高温生成方案，再低温精炼执行

第 7 章 上下文工程（Context Engineering）

7.1 为什么上下文工程更重要

2024 年后行业共识：模型能力越来越强，决定输出质量的关键从"怎么问"变成了"给模型看什么"。上下文工程 = 提示词设计 + 检索增强 + 记忆管理 + 工具结果注入。

7.2 系统提示设计最佳实践
  1. 身份定义：明确角色和专业领域
  2. 能力边界：能做什么、不能做什么
  3. 行为规范：输出风格、安全规则、格式要求
  4. 工具说明：可用工具及使用规则
  5. 保持精简：只放真正需要常驻的内容
7.3 对话历史管理策略
  • 固定窗口：保留最近 N 轮（简单但可能丢关键信息）
  • 摘要压缩：定期总结历史替换原文（省 token，可能丢细节）
  • 混合策略：系统提示 + 最近 N 轮 + 关键信息摘要
  • 向量检索历史：历史向量化，按需检索相关轮次
7.4 上下文窗口黄金布局
┌──────────────────────────────────────┐ │ 系统提示（角色+核心规则） 5~10% │ ├──────────────────────────────────────┤ │ 关键背景/检索结果（置顶） 20~30% │ ├──────────────────────────────────────┤ │ Few-shot 示例 10~15% │ ├──────────────────────────────────────┤ │ 对话历史 30~40% │ ├──────────────────────────────────────┤ │ 当前用户输入+输出格式要求 5~10% │ ├──────────────────────────────────────┤ │ （预留输出空间） 15~20% │ └──────────────────────────────────────┘
关键原则最重要信息放开头和结尾；中间是"注意力盲区"；输出空间必须预留足够。

第 8 章 提示词调试与优化

8.1 常见问题诊断表
症状可能原因调试方向
输出格式不稳定约束不够强/示例不足加强格式+Few-shot+结构化API
幻觉（编造事实）缺真实上下文加入RAG/要求引用/降temperature
忽略部分指令指令太多/关键在中间精简指令/关键置顶或置底/编号
推理错误未触发思考加入CoT/降温/Self-Consistency
风格不一致角色模糊/缺示例细化角色+风格示例+否定约束
8.2 迭代优化方法论（ADDIE）

Analyze 分析 → Design 设计 → Develop 开发 → Implement 实施 → Evaluate 评估。

8.3 优化 Checklist
  • 角色是否具体且相关？
  • 任务描述是否单一明确？
  • 输入数据是否用分隔符隔离？
  • 是否提供了 2~5 个高质量示例？
  • 输出格式是否有明确约束？
  • 约束条件是否具体可执行？
  • 关键指令是否在开头或结尾？
  • temperature 是否匹配任务类型？
  • 是否处理了边界情况？
  • 是否有评测集验证效果？
8.4 调试五技巧

二分法（逐步删除定位问题）、对比法（多版本同时跑）、追问法（问模型"为什么这么回答"）、日志法（记录每次输入输出）、最小复现（最简单输入复现问题）。

第 9 章 评测体系与质量保障

9.1 评测集构建
  • 正常用例（60%）：典型输入
  • 边界用例（20%）：空输入、超长、特殊字符
  • 对抗用例（15%）：Injection、歧义、恶意输入
  • 回归用例（5%）：历史问题案例，防回退

目标积累 100~500 条，从真实用户日志采样。

9.2 评测指标
类型指标适用场景
精确匹配Exact Match、准确率分类、提取
语义相似度BLEU、ROUGE、BERTScore翻译、摘要
LLM-as-Judge强模型打分开放式生成、代码质量
业务指标转化率、满意度、审核通过率线上效果
效率指标token数、延迟、成本工程优化
9.3 LLM-as-Judge 实践
请根据以下标准打分（1-10分）：
1. 准确性 2. 完整性 3. 格式 4. 清晰度
参考回答：{reference}
待评回答：{candidate}
输出 JSON：{"accuracy":0-10, "overall":0-10, "reason":"..."}
注意LLM-as-Judge 有位置偏见（倾向给第一个打高分），需随机化顺序或成对比较。
9.4 自动化评测流水线

代码提交 → 触发 CI → 运行评测集 → 生成报告 → 对比基线 → 达标则合并。工具：Promptfoo、Ragas、DeepEval、LangSmith。

第 10 章 主流模型 API 实战

10.1 OpenAI API（含兼容接口）
from openai import OpenAI
client = OpenAI(api_key="your-key")

response = client.chat.completions.create(
    model="gpt-4o",
    messages=[
        {"role": "system", "content": "你是一位资深 Python 开发者。"},
        {"role": "user", "content": "写一个快速排序函数"}
    ],
    temperature=0.2,
    stream=True
)
for chunk in response:
    if chunk.choices[0].delta.content:
        print(chunk.choices[0].delta.content, end="")

结构化输出：response_format={"type": "json_object"}

10.2 Anthropic Claude API
from anthropic import Anthropic
client = Anthropic(api_key="your-key")
response = client.messages.create(
    model="claude-3-5-sonnet-20241022",
    max_tokens=1024,
    system="你是一位资深全栈工程师。",
    messages=[{"role": "user", "content": "解释 React useEffect"}]
)

Claude 特点：长上下文强、代码质量高、支持 extended thinking。

10.3 国产模型

智谱 GLM-4（zhipuai SDK）、DeepSeek（兼容 OpenAI 格式，base_url 改 api.deepseek.com）、Kimi（兼容 OpenAI 格式，base_url 改 api.moonshot.cn/v1）。

10.4 API 工程最佳实践
  1. 错误重试：tenacity 指数退避
  2. 超时控制：流式 60s+，非流式 30s
  3. 并发控制：asyncio + 信号量
  4. 成本监控：记录 token 用量和费用
  5. 降级策略：主模型失败切备用
  6. 缓存：相同输入缓存（temperature=0 才安全）

第 11 章 提示词管理与版本控制

11.1 提示词即代码（Prompt as Code）
prompts/ ├── common/ │ ├── system_base.md │ └── output_formats.md ├── code/ │ ├── review.md │ ├── generate.md │ └── debug.md ├── product/ │ ├── prd_write.md │ └── requirement_analysis.md └── tests/ ├── review_test_cases.json └── generate_test_cases.json
11.2 提示词文件格式
---
id: code_review_v3
version: 3.1.0
model: gpt-4o
temperature: 0.2
max_tokens: 2048
description: 代码审查提示词，关注 bug、性能、安全

你是一位资深代码审查专家...
11.3 A/B 测试

用户请求 → 随机分配（50% A / 50% B）→ 记录分组 → 收集指标 → 统计显著性。关键指标：任务成功率、用户满意度、人工修正率、token 成本。

11.4 管理工具

LangSmith/LangHub、PromptLayer、Helicone、Dify/Coze、纯 Git+CI（最灵活）。

第 12 章 LangChain / LlamaIndex 框架

12.1 LangChain 核心概念
概念说明
Model封装 LLM 调用
Prompt Template提示词模板，变量注入

第 13 章 RAG 与知识增强

13.1 RAG 全流程
文档 → 切分 → 向量化 → 存入向量库 ↓ 用户问题 → 向量化 → 相似度检索 → 重排序 → 组装上下文 → LLM 生成
13.2 文档切分策略
策略适用优缺点
固定长度通用简单，可能切断语义
递归字符通用保持段落完整，推荐
按标题/章节结构化文档保留文档结构
滑动窗口重叠需上下文连贯减少边界信息丢失

推荐：chunk_size=500~1000 token，overlap=50~100 token。

13.3 检索优化五法
  1. 混合检索：向量 + BM25 关键词，取并集
  2. 重排序：Cohere Rerank / bge-reranker
  3. 查询改写：LLM 改写用户查询提升召回
  4. 多路召回：同时检索多个知识库
  5. 父文档检索：检索小块返回父文档
13.4 幻觉控制
  • 要求引用来源（标注每个事实来自哪个文档）
  • 严格约束"只能基于上下文回答，不知道就说不知道"
  • 置信度评估（模型对回答打分）
  • 事实校验（第二个模型验证事实是否在上下文中）
13.5 RAG 提示词模板

参考资料：
{retrieved_documents}

问题：{question}

第 21 章 资深岗面试题库

21.1 基础概念题

Q1：什么是提示词工程？和传统 NLP 的区别？

答题要点：通过设计输入引导 LLM 输出的工程方法。区别：不需标注数据和训练、迭代快、模型能力强但不可控性高、更强调工程化和评测。

Q2：解释 Token、上下文窗口、temperature。

Token 是基本处理单位；上下文窗口是一次能处理的最大 token 数；temperature 控制输出随机性，0 确定，越高越发散。

Q3：Zero-shot、Few-shot、CoT 的区别和适用场景？

Zero-shot 直接给指令（简单任务）；Few-shot 给示例（格式学习/分类）；CoT 逐步推理（数学/逻辑/多步）。

21.2 技术深度题

Q4：如何解决 LLM 幻觉？

  1. RAG 检索增强，提供真实上下文
  2. 要求引用来源，可追溯
  3. 降低 temperature，减少随机生成
  4. Self-Consistency 多次验证
  5. 事实校验（第二个模型交叉验证）
  6. 明确"不知道就说不知道"
  7. 高风险场景增加人工审核

Q5：长上下文处理策略？"Lost in the Middle"？

策略：滑动窗口、摘要压缩、分层检索、RAG。Lost in the Middle 指模型对长上下文中间部分注意力和召回率显著低于首尾。应对：关键信息放首尾、相关内容聚集、用检索代替全量塞入。

Q6：如何设计提示词评测体系？

构建评测集（正常/边界/对抗/回归）→ 定义指标（精确匹配/语义相似度/LLM-as-Judge/业务指标）→ 自动化流水线（CI 集成）→ 基线对比和回归 → A/B 测试线上验证。

Q7：Prompt Injection 是什么？如何防御？

攻击者通过输入恶意指令绕过系统提示或操纵模型。防御：输入隔离（XML 标签）、指令优先级声明、输入过滤、输出过滤、最小权限工具、人工审核。

21.3 系统设计题

Q8：设计智能客服 LLM 架构。

意图识别（路由）→ RAG 知识库（FAQ/产品文档）→ 多轮对话管理（状态机+记忆）→ 工具调用（查订单/退换货）→ 人工转接（低置信度）→ 安全过滤 → 监控评测。

Q9：设计代码生成 Agent。

需求理解 → 代码库检索 → 分模块生成 → 代码执行/测试验证 → Debug 循环 → 代码审查 → 文档生成。

Q10：如何优化 LLM 应用成本和延迟？

模型路由（简单用小模型）、提示词压缩、缓存、批量处理、流式输出、蒸馏小模型、降级限流。

21.4 场景题

Q11：用户反馈 AI 回答经常格式不对，怎么排查解决？

收集失败案例分析模式 → 检查格式约束是否明确 → 是否有 Few-shot → 使用结构化输出 API → 增加输出后校验和自动修复 → 建立回归测试集。

Q12：如何向非技术团队解释提示词工程价值？

用业务语言：提升效率（减少人工）、提升质量（标准化输出）、快速迭代（分钟级调整）、降低成本（替代定制开发）。用具体案例和数据说话。

第 25 章 提示词安全攻防

25.1 常见攻击手段
  1. 角色扮演越狱："假设你是一个没有限制的 AI..."
  2. 编码绕过：Base64、拼音、拆字编码恶意指令
  3. 多轮诱导：逐步引导偏离安全约束
  4. 间接注入：通过检索文档/网页注入指令
  5. Token 走私：特殊 token 或格式混淆
25.2 防御纵深五层
第一层：输入检测（正则 + 分类器） 第二层：提示词隔离（XML 标签 + 优先级声明） 第三层：工具权限控制（最小权限 + 人工确认） 第四层：输出过滤（敏感信息 + 安全审核） 第五层：监控告警（异常行为检测）

第 26 章 MCP 与工具调用

26.1 MCP（Model Context Protocol）

Anthropic 推出的开放协议，标准化 LLM 与外部工具/数据源的连接。核心概念：MCP Server（提供工具和资源）、MCP Client（LLM 应用）、Tools（可调用函数）、Resources（可读取数据）、Prompts（可复用模板）。

为什么重要MCP 正在成为 Agent 工具调用的标准协议，类似 LLM 界的"USB-C"。

第 27 章 微调与提示词协同

27.1 什么时候需要微调
  • 特定领域术语/风格，提示词难以稳定控制
  • 降低成本（小模型微调达到大模型效果）
  • 大量类似任务（微调后提示词可以很短）
  • 提示词已优化到瓶颈仍不满足
27.2 三者组合策略
微调负责：领域知识、术语、风格、格式习惯 提示词负责：具体任务指令、动态上下文、约束条件 RAG 负责：实时事实、私有数据
27.3 微调数据准备

质量 > 数量（500 条高质量 > 5000 条低质量）；格式与实际使用一致；覆盖多样性；包含边界和难例；提示词生成 + 人工审核。
